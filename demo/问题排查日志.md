## 问题 1：勾选「LLM 智能配对」后任务一直卡在「比对中」（running）

**日期**：2026-08-20

### 现象

- 前端创建任务时勾选「LLM 智能配对」（`fuzzy_llm=true`），任务一直停在 `status=running / stage=比对 / progress=0.4`，不再前进。
- 后端日志里**没有** `[llm]` 报错打印，也没有回退痕迹。
- 不勾选「LLM 智能配对」（`fuzzy_llm=false`）时，纯规则匹配几秒出结果，正常。

### 排查过程

1. **排除僵尸任务**：曾有旧后端进程被关闭后遗留的 running 任务（后端 `recover()` 只恢复状态、不重跑任务），会永远停在 running。但本次卡住的任务是新后端上创建的，非僵尸。

2. **排除文件问题**：上传文件 magic bytes 为 `504B0304`（合法 .docx），解析正常（orig 159 行 / plm 175 行）。

3. **确认 LLM 网关连通**：`https://inner-apisix.hisense.com/higpt-new/v1` 可访问，HTTP 200，0.5s 内响应（需带 `?user_key=` 参数，否则 401）。

4. **锁定模型行为**：`deepseek-v4-flash` 是**推理模型**，响应里先输出大量 `delta.reasoning_content`（思考过程），最后才输出 `delta.content`（正式回答）。

5. **实测复现**：用真实清单数据（残余候选 50 orig + 66 plm，prompt 19571 字符）调 LLM，结果：
   ```
   75 秒后强制中断 | chunks 5118 | reasoning_content 53924 字 | content 0 字
   ```
   模型陷入无限思考，一直吐思考过程、一个字的正式答案都不给。

6. **对比历史确认是间歇性异常**：同一份文件、同样 47/63 行残余候选：
   - 8/18 11:00：正常返回（`raw` 是正常 JSON，秒出）
   - 8/20 13:52：卡死（无限思考）
   - 8/20 14:12：又恢复正常

### 根因

两层原因叠加：

1. **模型层（主因）**：`deepseek-v4-flash` 推理模型偶发「陷入超长思考」——对同一个 fuzzy 配对 prompt，大多数时候秒出答案，少数时候持续输出海量 `reasoning_content` 而不给 `content`，持续十几分钟甚至更久。

2. **代码层（放大器）**：`_call_llm` 用 `stream=True` + `resp.iter_lines()` 读流，`requests` 的 `timeout=60` 对流式是「两次读取之间的空闲超时」而非总超时——只要服务器持续吐思考片段，就**永不超时**。于是任务无限阻塞在 LLM 调用上。

### 修复

改 `compare_core/suggester/llm_suggester.py`，加两道硬性熔断：

| 熔断 | 阈值 | 说明 |
|------|------|------|
| wall-clock 总超时 | `_LLM_TOTAL_TIMEOUT = 60.0`（秒）| 从发请求起计时，超过即中断 |
| 思考量熔断 | `_LLM_MAX_REASONING_CHARS = 10_000`（字）| `reasoning_content` 累计超阈值仍未出答案即中断（正常推理仅几百~一两千字）|

熔断抛 `_LLMAbort`，`_call_llm` 捕获后**不重试**（模型无限思考，重试无意义），直接回退规则匹配。

效果：模型正常时不受影响；模型抽风时最多 60 秒自动降级，不再无限卡死。

### 涉及文件

- `compare_core/suggester/llm_suggester.py`（`_LLMAbort`、`_read_sse_stream`、`_call_llm`）

### 后续建议

- 若长期不再需要 AI 模糊配对，可默认关闭 `fuzzy_llm`（前端不勾选，纯规则 + 型号集合匹配已覆盖大部分场景）。
- 若想根治「推理模型思考过长」，可在 `.env` 换用非推理模型（需先确认聚好看网关有哪些可用模型）。
