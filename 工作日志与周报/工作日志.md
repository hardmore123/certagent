## 三.6、问题根因分析与改进策略（2026-07-17）

针对样例运行发现的三类输出问题，查代码 + fixture 量化定位根因。分析脚本：`tests/analyze_issues.py`。

### 问题② 合并文件中间大量不间断缺失 —— 【P0 正确性 bug】
- **根因**：`compare_core/differ/diff_engine.py` 用 `orig_idx.setdefault(match_key, row)` 按 `关键件名称+型号` 字典去重，同键后续行被丢弃；`docx_writer` 又每个 diff 只输出一行。
- **实测证据**：表1 **438 行 → 仅 175 个唯一(名称+型号)键 → 丢失 263 行**（55 个键重复）。重灾：`内部布线(电源到屏驱动)|/` ×39、另一 `内部布线…|/` ×36、`X电容|cmpp` ×16（型号为"/"或同型号跨多位号/证书号的行被折叠）。
- **改进**：① 匹配键行级唯一（加 位号+规格+证书号 或行序）；② 合并输出保留全部行，diff 只用于"判断新增/差异"，不决定输出行数；③ `setdefault` 去重改为行级对齐（列表而非 dict 覆盖）。

### 问题① 格式错误 / 输出不规范 —— 【P1】
- **根因**：`compare_core/writer/docx_writer.py` 用固定 8 列 `_COLS` 拍平，丢弃分组标题行/表2/位号/备注/原列序/合并单元格；输出自制 .docx 与样例 .doc 结构不一致。
- **改进**：① 以原文档结构为模板输出（表1 十列 + 表2 独立 + 分组行）；② 更稳：以 PLM 导出 .docx 为基底"在原档上改"，仅标注新增/差异，保留原排版；③ 建输出规范化层（列 schema 固定、单位/符号规范、空值占位、繁→简）。

### 问题③ 存在繁体字 —— 【P1】
- **纠正**：先前快速扫描报"203 处繁体"为误报（集合误含"器/线/构"等简体字），该数字作废；准确检测需专业库。
- **根因**：`compare_core/differ/normalize.py` 只做全半角+波浪号+顿号，**无繁→简**；源 .doc 混入的繁体字原样透传。后果：匹配层繁/简变体判为不同（假差异）、输出层繁简混排。
- **改进**：引入 `opencc`（t2s）——① `normalize` 加繁→简，折叠繁简变体；② 输出按业务要求统一转简体（可配置）。

### 修复优先级
| 问题 | 严重度 | 位置 | 优先级 |
|---|---|---|---|
| ② 大量缺失(丢 263 行) | 高·数据错误 | diff_engine + docx_writer | **P0** |
| ① 格式不规范 | 中·不可交付 | docx_writer | P1 |
| ③ 繁体字 | 中·一致性 | normalize | P1 |

- **建议顺序**：先修 ②（正确性：匹配键行级唯一 + 合并保留全部行），再 ③（加 opencc 归一化，顺带改善匹配），最后 ①（输出模板化/在原档改，工作量最大）。
- **数据/脚本位置**：`tests/analyze_issues.py`（量化脚本）、`runs/sample_out/`（样例运行产物，已暴露问题）。

## 三.7、修复问题②：合并文件行丢失（2026-07-17）

- **任务**：修复"按 名称+型号 去重导致 263 行丢失"的正确性 bug（P0）。
- **改法**：
  1. 重写 `compare_core/differ/diff_engine.py`：
     - 匹配键行级化——rich 键(名称+型号+位号+规格+证书号+table) 判"同一物理行"，loose 键(名称+型号) 判"内容变更"；
     - **行级多重集对齐**：以 PLM(变更后) 为基底逐行匹配，rich 命中→SAME、loose 命中→CHANGED、无命中→ONLY_PLM；原报告未消费行→ONLY_ORIG 追加；
     - 每个 DiffItem 对应"一行输出"，key 全局唯一（`same-1`/`changed-2`…），不再折叠。
  2. `compare_core/writer/docx_writer.py`：非重复项（ONLY_PLM/ONLY_ORIG/CHANGED）均标红加粗，来源标签细化（PLM导出/原报告/两侧(差异)）。
- **验证结果**：
  - `smoke.py`：`{same:1, changed:1, only_plm:2, only_orig:1}`（行级），`SMOKE_OK` ✅
  - `real_e2e.py`：`{same: 475}`——**由折叠后的 193 恢复为完整 475 行**，行丢失消除，`REAL_E2E_OK` ✅
  - 静态检查：diff_engine / docx_writer 无诊断错误。
- **效果**：合并清单不再"中间大量缺失"，输出行数 = PLM 全部行 + 原报告独有行。
- **遗留**：问题①（输出格式/结构规范化）、问题③（繁体字 opencc 归一化）待修；本次未在真实"有差异"样例上验证 CHANGED/标红（当前样例仍为同基线）。

## 三.8、修复问题③：繁体字（繁→简归一化）（2026-07-17）

- **任务**：源数据混入繁体字，导致匹配层假差异、输出层繁简混排（P1）。
- **改法**：
  1. 引入 `opencc-python-reimplemented`（t2s）；`compare_core/differ/normalize.py` 新增 `to_simplified()`（懒加载单例 + 无库时优雅降级原样返回）。
  2. **匹配层折叠**：`normalize()` 先做繁→简，繁/简变体归一，避免假差异。
  3. **输出层统一**：`docx_writer._safe()` 按 `config.OUTPUT_SIMPLIFIED`（默认 true，可 env 关闭）转简体；`config.py` 增开关；`.env.example`/`requirements.txt` 同步。

    - `input_name_model_only` 15：名称+型号能找到输入，完整身份对不上（业务对同名同型号行做了字段级改动）
    - `demo_identity_only_content_diff` 6
    - `input_identity_but_not_demo+strict_input_match` 2
    - `not_in_input_identity` 1（唯一真"凭空补录"）
- **结论**：27 行差额的根因不是解析漏行，也不是 writer 少写行，而是**业务合并时做了字段级修改和整组结构调整**，物理行 diff 无法表达这种业务语义。

### 2) 关键件组抽象原型 · `tests/prototype_group_aggregation.py`
- **动机**：观察到"电源单元换型"这一件业务事件被物理行 diff 拆成了 20+ 条 ONLY_ORIG / ONLY_PLM，说明匹配粒度错了。
- **做法**：按 `(表号, 分组标题, 关键件名称)` 聚合成关键件组，组内选型按 `(型号, 位号, 规格, 证书号)` 做多重集对齐。
- **关键数据**（`runs/group_prototype_2026-07-28/group_prototype.md`）：
  - 43 组，5 种状态：SAME 6、REPLACED 8、SHRUNK_BY_PLM 3、ONLY_ORIG 11、ONLY_PLM 15
  - **41 条严格未覆盖行中 40 条（97.5%）落在非 SAME_GROUP 组**——组级视角识别为业务动作
  - `input_name_model_only` 15 条 100% 命中非 SAME_GROUP
  - `53772-A 型机内电源单元上元器件` 分组下 10 个子组整消 + `55431-F 内电源单元上元器件` 分组下 10 个子组整增——正是业务"电源单元换型"这一件事
- **结论**：关键件组是契合业务语义的最小单元；组级 diff 数据量从 205 条物理行 → 43 组，5 倍压缩。

### 3) 组级 diff → 业务模板归纳实验 · `tests/experiment_group_suggest.py`
- **动机**：验证"数据 shape 对了之后，即使 Mock 也能大幅改善对照表质量"。

- **关键数据**（`runs/exp_group_suggest_2026-07-28/experiment.md`）：

  5. 输出前需自检：条目数 = 5 且所有非 SAME 组都被覆盖
- 结果：**LLM 返回 5 条条目，业务模板覆盖 5/5** ✓

## 三.15、第三级匹配：关键件名称前缀匹配落地（2026-07-28）

**背景**：东芝样例中，原报告有一行 `电线组件 / HL-006L 10A 250V~+HL-110...`，PLM 导出侧同一组件命名为 `电线组件(0.5平方毫米线径的电线组件，长度小于2m)`（名称加了括号限定）。当前两级匹配（rich key / loose key）因名称不同无法配对，该行被标为 ONLY_ORIG 追加到输出末尾，位置和归组不正确。

### 1) 只读原型验证 · `tests/prototype_fuzzy_name.py`

三轮迭代：

| 版本 | fuzzy 条件 | 命中 | 副作用 |
|---|---|---:|---|
| v1 要求型号相同 | table + group 兼容 + 名称包含 + 型号相同 | 0 | - |
| v2 放宽型号 + 子串 + 1/3 长度比 | table + group 兼容 + 名称子串 + 短名/长名 ≥ 1/3 | 0（"电线组件"4字/27字=15% < 33%） | - |
| v3 前缀 + 放宽长度比 + 名称不完全相同 | table + group 兼容 + 前缀 + 名称不同 | 12（含 11 条同名跨组误配） | 高 |
| v4 收紧：group 完全相同 | table + group 完全相同 + 前缀 + 名称不同 | 2（电线组件 + PCB 跨组） | PCB 跨组 |
| **v5 最终**：group 完全相同 + 不跨组 | table + group 完全相同 + 前缀 + 名称不同 + 短名≥3字符 | **1** | **零** |

最终命中 1 条：`电线组件` → `电线组件(0.5平方毫米线径的电线组件，长度小于2m)`，零副作用。

### 2) 落地到 `diff_engine.py`

**新增代码**：
- `_name_is_prefix(a_name, b_name)`：判断两个名称 normalize 后是否有前缀关系（且不完全相同、短名≥3字符）
- `_fuzzy_name_compatible(p, o)`：完整约束（同表 + group 完全相同 + 名称前缀关系）
- `take_fuzzy(p)`：从同 table 的 orig 行池里找第一个满足条件的未消费行
- `run_diff` 主循环增加第三级：`rich → loose → fuzzy → ONLY_PLM`

**设计约束**：
- group 必须完全相同（都为空 或 都有值且相同）—— 不允许跨组配对
- 名称不完全相同（相同的行应已被 loose key 处理，走到 fuzzy 的同名行是跨组/已消费的，不应强行配）
- 用前缀（`startswith`）而不是子串（`in`）—— 避免 "Y电容" 匹配到 "X电容Y组件"

## 三.19、python-docx 解析路线落地（根治 Word COM 问题）（2026-07-28）

### 背景
Web 服务里 Word COM 频繁报错（`AttributeError: Open/Close/Visible`）。根因：Word COM 是 STA 单线程单元模型 + 依赖本机 Word 进程，在 asyncio 线程池里必然不稳定。`CoInitialize`/`DispatchEx` 只是补丁。根治方案：换成纯 python-docx 解析 `.docx`（无 COM，线程安全）。

### 改动（不删除任何旧文件）
| 文件 | 变更 |
|---|---|

## 三.20、.doc → .docx 自动转换（多级策略，子进程隔离）（2026-07-28）

### 背景
三.19 用 python-docx 根治了 COM 解析问题，但老 `.doc` 二进制仍需手动"另存为 .docx"。本次实现自动转换，用户上传 `.doc` 也能自动处理。

| 1 | LibreOffice headless | 装了 soffice | 跨平台、无需 Word、`soffice --headless --convert-to docx` |
| 2 | Word COM 子进程 | Windows 有 Word | 独立 python 子进程跑 COM 脚本，转完即退 |
| 3 | 抛错提示 | 都没有 | 提示装 LibreOffice 或手动另存为 |

`ensure_docx(path)`：
- `.docx` → 原样返回
- `.doc` → 依次尝试 LibreOffice → Word COM 子进程
- 都失败 → 明确错误信息

### 集成
- `compare_core/parser/__init__.py`：`parse_document(path, auto_convert=True)` 遇 `.doc` 自动调 `ensure_docx` 转换后用 python-docx 解析；转换失败回退直接 COM
- `webapi/runner.py`：`_load_one` 三级分派（JSON → docx → 自动转换 .doc）

产物：`runs/converter_test/`

- **老 .doc 现在能自动转换**，用户上传 .doc 无需手动另存为

## 三.21、修复贪心顺序错配 bug（逐行三级 → 分趟匹配）（2026-07-28）

### 问题现象
Web 差异确认页发现"内部布线(电源到屏驱动)"等组出现**整体错位一格**的错配：
- A 第1行(证书 CQC23011379631) ↔ B(证书 CQC23011381271)
- A 第2行(证书 CQC23011381271) ↔ B(证书 CQC22011372272)
- A 第3行(证书 CQC22011372272) ↔ B(证书 CQC23011377752)

这些行名称相同、型号都是 `/`，仅规格材料/证书号不同。本该按证书号精确配对（SAME），却被错配成 CHANGED。

### 根因：贪心顺序错配
旧代码是**逐行三级匹配**（对 A 每行依次 rich→loose→fuzzy）：
```
A 第1行 rich 找不到 → 退到 loose → loose key "内部布线|/" 全组相同
    → 抢走 B 第一个未消费行(CQC23011381271) ❌
A 第2行 rich 本该匹配 B 的 CQC23011381271
    → 但已被 A 第1行 loose 抢走 → rich 失败 → loose 抢下一个 ❌
→ 连锁错位
```
本质：loose 匹配抢走了本该留给后面行做 rich 精确匹配的 B 行。

### 修复：分趟匹配
`compare_core/differ/diff_engine.py` 的 `run_diff` 从"逐行三级"改为"分趟"：
1. **第一趟**：所有 A 行先做 rich 精确匹配（证书号/位号/规格全同 → SAME）
2. **第二趟**：剩下未匹配的做 loose（同名同型号内容不同 → CHANGED）
3. **第三趟**：仍未匹配的做 fuzzy（名称细化 → CHANGED）
4. 按 A 原序生成 DiffItem，未匹配 A 行 → ONLY_ORIG，B 未消费 → ONLY_PLM

关键：先全体 rich，证书号相同的行优先精确认领 B 对应行，不会被别的行的 loose 抢走。

### 验证结果（东芝真实 docx）
| 指标 | 修复前（逐行三级）| 修复后（分趟）| 变化 |
|---|---:|---:|---:|
| SAME | 52 | 99 | **+47** |
| CHANGED | 58 | 11 | **-47** |
| ONLY_ORIG | 49 | 49 | 0 |
| ONLY_PLM | 65 | 65 | 0 |

**47 行**从错配的 CHANGED 修正回正确的 SAME。行总数不变（不丢行）。

- `smoke.py` 通过（`same:1, changed:1, only_orig:1, only_plm:2`）
- 组级 diff 43 组、对照表 5/5 不受影响（组级抽象本就与行级顺序无关）
- get_diagnostics 无错误

### 意义
这是一个真正的正确性 bug 修复。之前 CHANGED 数虚高（58），大量本该"相同"的行被误判为"内容不同"并错误配对展示 A/B。修复后 CHANGED 回归真实水平（11），差异确认页不再出现错位对比。

## 三.25、数据守恒审计节点 + repair 补录分支（LangGraph 条件边）（2026-07-30）

### 需求
在 LangGraph 流程中加一个校验节点：走完流程后检查输入 A/B 的每一行及内容是否都保留了，
若丢失或异常给出建议并处理。

### 设计：apply 之后插入 audit 节点，三层校验
| 层 | 检查内容 | 手段 |
|---|---|---|
| 引擎层 | A/B 每行是否被某个 diff 引用 | `id()` 引用集比对，未引用=解析/比对丢行 |
| 决策层 | 行归属 diff 保留/拒绝；SAME/CHANGED 被拒会丢双侧信息 | 统计 reject |
| 物理层 | 回读整合 docx 实际数据行 vs 预期保留行 | python-docx 计数（排除表头/分组标题行）|

**分级 + 分支（条件边，回答“丢了怎么办”）：**
- `critical`（引擎丢行 / 物理少行）→ **repair 补录节点**：把疑似丢失行追加到文档末尾
  「⚠审计补录（疑似丢失，需人工复核）」红字表，保证零物理丢失 → memory
- `warning`（SAME/CHANGED 被拒 / 物理多行疑似重复）→ 不阻断，进报告给建议 → memory
- `ok` → 直接 memory

### 新增 LangGraph 拓扑
```
... → apply → audit → [条件边 _route_after_audit]
                        ├─ critical → repair → memory → END
                        └─ 否则      →          memory → END
```

### 改动文件
| 文件 | 变更 |
|---|---|
| `compare_core/models.py` | 新增 `AuditReport`（status/丢失清单/mismatch/建议 等）|
| `compare_core/differ/audit.py`（新）| `run_audit()` 三层校验 + 分级 + 建议；`_count_output_rows` 回读 docx |
| `compare_core/writer/docx_writer.py` | 新增 `append_audit_supplement()` 补录附录表 |
| `compare_core/nodes.py` | 新增 `audit_node` / `repair_node` |
| `graph/build.py` | 加 audit/repair 节点 + `add_conditional_edges` 条件边 |

### 改动
| 文件 | 变更 |
|---|---|

### 原理（守恒等式）
以 B(新版本) 为骨架逐行匹配 A(旧版本)：
- 相同/内容不同：A、B 各一行配对，合并成 1 个 diff
- B独有(only_plm)：新增；A独有(only_orig)：旧版本保留
- 故 A = same+changed+only_orig，B = same+changed+only_plm，合并输出 = 四类之和
- same/changed 各合并一行，所以输出总数 < A+B

## 三.31、流程梳理 + 分片必要性 + diff 是否用 LLM 的结论（含 fuzzy 候选提名方案）（2026-07-30）

### 一、流程重新梳理（重点 LangGraph）

整体链路（一个 state 贯穿，三种编排——LangGraph 图 / 顺序 pipeline / Web 后端——共用同一套节点函数）：
```
START → parse → judge → suggest → human_review(interrupt) → apply → audit → [条件边] → memory → END
                                                                              ├ critical → repair → memory
                                                                              └ 否则      →         memory
```

| 节点 | 干什么 | 产出 |
|---|---|---|
| parse | 解析 Word（.docx 直读 / .doc 先转换）→ 结构化 Row | rows_orig / rows_plm |
| judge | 行级三级匹配(rich→loose→fuzzy)产出 diffs + 组级聚合产出 group_diffs | diffs / group_diffs |
| suggest | 规则给逐行动作 + **LLM 从组级 diff 归纳对照表（唯一 LLM 调用）** | suggestions / changes |
| human_review | interrupt() 挂起，抛差异等用户决策 | decisions |
| apply | 按决策生成 整合清单 + 对照表 两份 Word | out_merged / out_compare |
| audit | 数据守恒三层校验(引擎/决策/物理) | audit_report |
| repair | critical 时补录丢失行到附录(自愈) | 更新 out_merged |
| memory | 决策落盘 JSONL 供反馈学习 | — |

LangGraph 三个关键点：
1. **人在环** = `interrupt` + `Command(resume=...)`，图暂停存 checkpoint，用户决策后原地恢复；
2. **条件边** = audit 后唯一分叉：critical → repair → memory，否则直接 memory；
3. **节点复用** = 图/顺序/Web 调同一批 `nodes.py` 函数，改一次三处生效。

Web 后端不用 interrupt，用 HTTP 两段式（`/diffs` 看 → `/decisions` 提交）天然实现人在环，节点逻辑一致。

### 二、分片处理必要性结论：暂不需要（保留为扩展点）

- 全流程**只有 suggest 调 LLM**；送进去的不是原始几百行，而是组级 diff（205 行→43 组，drop_same 后 37 组，prompt 约 9500 字符），远小于 DeepSeek V4 上下文。
- **关键件组抽象本身就是"语义分片"的更优替代**：按字符切片会切断"电源单元换型"这类跨行业务动作，组抽象反而聚成一条。
- **需要分片的场景**：① 单份清单极大（上千组超上下文）→ 按"表→分组"自然切片、组边界不破坏语义、分片归纳后合并；② 批量文件并发限流（并发问题，非上下文问题）。
- 结论：暂不做分片，保留组抽象；真遇超大清单时按分组切片是现成扩展点。

### 三、diff 对比过程是否用 LLM：核心不用，仅 fuzzy 层可做"候选提名"

**核心 diff（匹配 + 分类）保持确定性代码**，理由：可复现（同输入同输出）、可审计（守恒依赖"行被哪个 diff 引用"的确定关系）、零幻觉（合规清单一行不能错/多）、快且免费。LLM 的随机性与幻觉不适合"判去留"。

**分工定论**：
- diff（判去留）→ 确定性代码
- suggest（归纳对照表）→ LLM（语义活、容错高）
- decision（拍板）→ 人
- LLM 增强点 → 仅 fuzzy 层"候选提名"，不直接决策

### 四、LLM fuzzy 候选提名方案（拓展设计，未实现）

**要解决的痛点**：rich/loose 规则匹配不上、但业务上疑似"同一件"的行对——如 旧「电线组件」 vs 新「电线组件(0.5平方毫米线径…)」、同义不同写法、缩写/全称、参数顺序不同等。当前 fuzzy 仅靠"名称前缀"，覆盖有限。

**设计原则：LLM 只提名，不决策**
1. **触发范围收窄**：只对"两级确定性匹配后仍未配对"的残余行（ONLY_ORIG × ONLY_PLM 候选池）调用 LLM，且限定同表、（可选）同组，避免全量两两比对爆炸。
2. **LLM 输出结构化候选**，不改 diff：
   ```json
   {"pairs": [
     {"orig_key": "...", "plm_key": "...", "same_part": true,
      "confidence": 0.0-1.0, "reason": "名称为同一物料的详略写法"}
   ]}
   ```
   只返回"疑似同一件"的候选对 + 置信度 + 理由，**不返回 same/changed 判定**。
3. **确定性引擎登记**：候选对回到 `diff_engine`，仅当置信度≥阈值(如 0.8)才**标记为"待确认配对"**（新增一个 `PENDING` 或复用 CHANGED + `low_confidence` 标志），仍走行级多重集消费逻辑，保证守恒不破。
4. **人工确认页确认**：候选在差异确认页高亮展示"AI 疑似同一件（置信度 X，理由 Y）"，用户点"接受配对/拒绝"；接受→按 CHANGED 合并，拒绝→各自保留为 ONLY_ORIG/ONLY_PLM。
5. **审计守恒不受影响**：无论 LLM 提名与否，每行仍被唯一 diff 引用，audit 三层校验照常；LLM 提名错了顶多是"该配没配/不该配提了"，由人拦截，不会丢行或造行。
6. **反馈闭环**：用户对候选的接受/拒绝写入 memory（feedback_store），后续可沉淀为别名表（如「电线组件」≡「电线组件(0.5平方毫米…)」），逐步减少对 LLM 的依赖。

**落地位置（若实现）**：
- `differ/diff_engine.py`：新增第 2.5 级"LLM 候选提名"（在 loose 之后、ONLY_* 定案之前），可用 flag 开关，默认关闭保持纯确定性；
- `suggester/llm_suggester.py`：新增 `propose_fuzzy_pairs(candidates) -> pairs`，复用 OpenAI 兼容接口 + 专用 prompt；
- 前端 ReviewPage：候选配对行增加"接受/拒绝配对"交互；
- `memory`：记录配对决策，供别名表沉淀。

**收益 vs 风险**：借 LLM 语义能力补 fuzzy 短板（同义/详略/缩写），同时保留可复现·可审计·守恒三条底线（LLM 不决策、人兜底、审计不依赖 LLM）。风险主要是额外 LLM 调用成本与延迟，故限定"仅残余候选池"触发、默认可关。

## 三.34、别名归一闭环：暂缓（决策记录）（2026-07-30）

### 决策
"把 `mine_aliases()` 产出的别名表在 diff 前做名称归一"——**暂时保留、先不做**。
`mine_aliases()` 已能产出别名对（三.33 验证），但"归一回灌"这一步本次不落地。

### 为什么值得做（留档，便于将来评估）
1. **省钱省时**：把"一次性 LLM 判断"沉淀为"永久查表"——确认过的语义等价，之后用查表（毫秒/免费/确定）替代 LLM（几秒/有费用/有随机），同类清单越跑命中率越高，LLM 调用越少。
2. **更稳可复现**：别名表确定，一旦沉淀结果恒定；LLM 有随机性。合规场景看重可复现。
3. **反馈变资产**：用户"接受配对"从只落 JSONL 变成真正反哺系统，闭环闭合。

### 为什么先不做（权衡与风险）
- **别名作用域存疑**：「电线组件」≡「电线组件(0.5…)」在东芝成立，换厂商/机型未必；需限定范围（同表/同组/同厂商）否则误归一。
- **样本太少易过度自信**：仅 1 次确认就沉淀风险高，需阈值（accepts≥N 且 rejects=0）。
- **合规回溯**：自动归一需可追溯"因别名表归并"，不能变黑盒。
- 当前 fuzzy 提名 + 人确认闭环已可用，别名归一属"优化项"非"必需项"，优先级可后置。

### 若将来做，推荐路线（保守）
仅在 **fuzzy 层前置**查别名表：匹配前命中即按"待确认配对"标记并**跳过 LLM 调用**，
仍走人工确认；不改 rich/loose 主匹配；别名沉淀带阈值。收益（省 LLM+可复现）大、风险小。

### 现状锚点
- `compare_core/memory/feedback_store.py`：`mine_aliases()` 已实现，产出 `{orig_name, plm_name, accepts, rejects}`。
- 归一接线点（将来）：`diff_engine.run_diff` 在 rich/loose 前，或 fuzzy 第三趟前置查表。

## 三.36、残余池漏配诊断 + "A/B 行对应判定规则"说明（2026-07-30）

### 一、残余漏配诊断（`tests/diagnose_residual_match.py`，只读）
把基线 diff 的 A独有(ONLY_ORIG 50 行) × B独有(ONLY_PLM 66 行) 交叉排查是否有"应匹配却漏配"。
6 类信号（强→弱）结果（东芝样例）：

| 信号 | 含义 | 命中 | 结论 |
|---|---|---|---|
| S1 归一后整行相同 | 本应 SAME | **0** | ✅ 无引擎 bug |
| S2 loose键相同 | 本应 CHANGED | **0** | ✅ 无漏配 |
| S3 名称+型号相同但跨组 | 同件分到不同组 | 20 | ⚠️ 业务有意不配（电源单元换型 53772-A↔55431-F）|
| S4 证书号相同 | 强信号 | 8 | 混合：部分同件异写法(AI该配)，部分共享系列证书号的不同物料(不该配) |
| S5 型号相同/名称不同 | 换名候选 | 0 | — |
| S6 名称前缀关系/同组 | 名称细化 | 1 | 电线组件 |

**关键结论**：
- 同组精确/宽松匹配层面**零漏配**（S1=S2=0），引擎干净。
- 未匹配主要是：跨组换型 20 对（业务要求保留，不合并）+ 少数同件异写法（AI 提名已能抓到，如后壳材料/PCB）。
- **证书号相同不能单独作合并依据**（S4 有反例：开关电源变压器 vs 开关变压器型号不同但共享证书号），故不将证书号做成自动匹配键是正确的。

### 二、A/B 行"对应判定规则"（正式说明，留档）
判定 = 归一化后字段键相等 + 一对一消费；只判等不打相似度分。

1. **归一化**：繁→简 + 全半角 + 去空格 + 波浪号/顿号统一（`normalize`）。
2. **两把键**：
   - Rich 键(7 字段)：`表号+分组+关键件名称+型号+位号+规格材料+证书号`
   - Loose 键(4 字段)：`表号+分组+关键件名称+型号`
3. **判定顺序（以 B 新版本为基准，分趟）**：
   - Rich 键相等 → 对应，SAME（完全一致）
   - 否则 Loose 键相等 → 对应，CHANGED（同件内容变了，记差异字段）
   - 否则（可选）LLM 提名疑似同一件 → 待人工确认
   - 否则 B 行 = ONLY_PLM（新增）；A 中未认领 = ONLY_ORIG（旧版本独有）
4. **一对一消费**：`used` 集合保证每个 A 行只对应一个 B 行；同名同型号的重复行用"列表+逐条领取"，不覆盖不乱配。
5. **分趟匹配**：全体先 Rich 再 Loose，避免宽松键抢走精确匹配的行。
6. **身份边界**：分组、表号进键 → 跨组/跨表一律不对应（保证电源单元换型这类不被误合并）。

**为什么只判等不打分**：认证清单要可复现·可审计·零误配；相似度会误判（"Y电容"≈"X电容Y"）。同名异写法的漏网交 AI 提名+人确认，不混进确定性主匹配。

## 三.39、"同名同型号"判定细节实测 + 一处记录纠正（2026-07-30）

### 判定方式
用 **Loose 键**：`t{表号} | normalize(分组) | normalize(关键件名称) | normalize(型号)`，
四段拼成字符串后**逐字符完全相等**才算"同名同型号"。只判等，无相似度分数。

### normalize 六步（实测输出）
```
'S1000 H'         -> 's1000h'          去空白
'S1000H'          -> 's1000h'          ← 与上相等
'電線組件'         -> '电线组件'         繁→简(opencc)
'250V～'          -> '250v~'           波浪号统一+小写
'PCB(主板，电源板)' -> 'pcb(主板,电源板)'  全角括号/逗号→半角
'PCB(主板、电源板)' -> 'pcb(主板,电源板)'  ← 顿号→逗号，与上相等
```
顺序：繁→简 → 全角转半角 → 波浪号(～/﹀→~) → 全角逗号与顿号→`,` → 去所有空白 → 转小写。
即空格/繁简/全半角/顿号/大小写差异都被折叠，不影响判定。

### 纠正三.32/三.35 的一处记录
此前把 PCB 那条 AI 提名的原因记为"型号空格差异(S1000H vs S1000 H)"——**不准确**。实测：
```
A旧 型号 'HH' -> loose键 t1||pcb(主板,电源板)|hh
B新 型号 'HH' -> loose键 t1||pcb(主板,电源板)|hh
loose 键相等? True   ← 这行本就在第2趟配成 CHANGED
```
LLM 提名的是另一条 PCB 记录：型号一格含多值（`S1000 H、S1000-2M` vs `S1000H、S1000-2M、S1150G`），
B 侧多了 `S1150G`，**整格字符串不等**才未配上。真正原因是"一格多型号、集合不同"，非空格差异。

### 已知局限（设计边界）
型号列常一格写多个型号，当前做**整格字符串比较**，不做型号集合比较。
只要一侧多/少一个型号即整格不等 → 判为两侧独有。此类场景正由 AI 提名 + 人确认兜底。
（若将来要收紧：可把型号按分隔符拆成集合做多重集比较，但会影响"多型号合并成一行"的既有语义，需业务确认。）

### 同名同型号多行的处理（实测数据）
同一 loose 键大量重复存在：
```
39 次: t1||内部布线(电源到屏驱动)|/
36 次: t1||内部布线(电源板到主板连接线,主板到扬声器的连接线)|/
 2 次: t1||绝缘垫片|/
```
（型号为 `/`，靠 位号/规格/证书号 区分。）处理：索引用**多重集**`键→[行...]` 而非字典覆盖，
每次只领取一条未被 `used` 认领的行 → 39 条各自配对，既不折叠成 1 条也不一对多。
这正是早期"438 行被折叠为 175 行、丢 263 行"bug 的根治机制。

## 三.40、修复：rich 命中但字段有差异被误判 SAME（正确性 bug）（2026-07-30）

### 问题现象（用户截图发现）
"后壳材料"、"扬声器外壳材料"等行被判为 **SAME（相同/自动保留）**，
但并排视图已高亮出 `认证标准` 实际不同（`GB/T 5169.12-2013` → `GB/T 5169.12-2024`）。
即"标着完全相同，却又高亮显示不同"——前后端口径矛盾，且变更被静默吞掉。

### 根因
Rich 键字段 = `表号+分组+关键件名称+型号+位号+规格材料+证书号`，
**不含 制造商 / 生产企业 / 认证标准 / 备注 / 本次使用**。
第 1 趟 rich 命中后直接判 SAME 并 `changed_fields=[]`，**从未复核这些字段**。
而前端并排视图 `SideCell` 自行逐字段比对，所以能高亮出差异 → 两边口径不一致。
后果：这些行按 SAME 自动保留（取 PLM 新版本值），人工在确认页完全看不到该变更。

### 影响面实测（东芝样例，修复前）
99 个 SAME 中 **7 行实际有字段差异**：
- `认证标准` 5 例（2013→2024 标准年份升级，正是截图案例）
- `制造商` 1 例（村田电子贸易有限公司 → 村田电子贸易（天津）有限公司）
- `备注` 1 例、`本次使用` 1 例

### 改动（`compare_core/differ/diff_engine.py`）
- 新增 `_VERIFY_FIELDS = ["位号","规格材料","制造商","生产企业","认证标准","证书号","备注","本次使用"]`
  —— 涵盖 rich 键未包含的全部实质内容列
- 第 1 趟 rich 命中后**增加内容复核**：`_compare_fields(o, p, _VERIFY_FIELDS)`
  - 有差异 → 升级为 **CHANGED**（带具体差异字段，交人工确认）
  - 无差异 → 才判 SAME

### 验证
- 修复后重跑诊断：SAME 中"实际有差异"= **7 → 0** ✓
- 分布：`same 99→92`、`changed 10→17`；待确认项 `126→133`（与预测完全一致）
- 守恒等式不变：A=same+changed+only_orig、B=same+changed+only_plm，审计 status=ok 225=225 ✓
- 回归：`smoke.py` 仍 `same:1,changed:1,only_plm:2,only_orig:1` SMOKE_OK
  （构造样例的 SAME 是真·完全相同，未被误升级 → 判定精准，无过度触发）
- `test_review_order.py` 顺序不一致处=0；`test_audit.py` 4 场景全过；
  `test_web_e2e.py` WEB_E2E_DONE、Web 端 `same 92 / changed 17` ✓

### 意义
1. **消除静默吞变更**：认证标准升版、制造商更名这类关键变更，现在必须经人工确认，符合认证合规要求。
2. **前后端口径统一**：前端能高亮出差异的行，后端必判 CHANGED，不再出现"相同却高亮"的矛盾。
3. 人工可在确认页看到 A/B 字段级对比后，自行决定接受（合并取新版本值）或拒绝。

## 三.41、版本快照 v3 + 相似度匹配可行性实验（结论：不可行）+ LLM prompt 留档（2026-08-03）

### 二、相似度匹配实验（`tests/experiment_similarity.py`，只读）
对残余池 A独有50 × B独有66（同表两两 3300 组合）打分。指标：名称 SequenceMatcher、
型号 SequenceMatcher、型号按分隔符拆集合 Jaccard、证书号相等、combo(名称0.5+型号0.5)。

**结论：相似度不可行——分数与"是否同一件"完全倒挂。**

| 对照组 | 业务应判 | combo 区间 |
|---|---|---|
| 同名跨组（熔断器/开关变压器/X电容，电源单元换型）105 对 | **必须拒绝** | **0.500 ~ 1.000**（大量满分 1.000）|
| 同组名称前缀关系（电线组件→电线组件(0.5平方毫米…)）11 对 | **应该接受** | **0.129 ~ 0.497** |

- 该拒绝的拿满分，该接受的最高 0.497，**两区间倒挂，不存在可用阈值**
- 阈值扫描（限同组）：任何阈值下"前缀关系命中"均为 **0**，因电线组件名称相似度仅 0.26（4字 vs 27字）
- 证书号相同 37 对，绝大多数是跨组熔断器/变压器（一证覆盖一系列），**不能作合并依据**

**根本原因**：相似度衡量字面接近，而"同一件"取决于业务语义——
①决定性因素是**分组**不是字面（跨组同名字面100%相同却是不同物料）；
②真正该配的反而字面差极远（4字 vs 27字）。

**保留现有设计**：归一化键相等（可复现/可审计/零误配）+ 分组作身份边界 + LLM 语义提名 + 人确认。
相似度唯一潜在用途：大候选池时给 LLM **粗筛排序**以缩短 prompt，但不能用于拍板。

### 三、当前 LLM prompt 留档

## 三.43、输出模板/格式/字号可配性现状与方案（记录，暂不实施）（2026-08-03）

### 现状：仅 2 个参数可配，其余硬编码
`compare_core/config.py` 可配项：
| 参数 | 默认 | 作用 |
|---|---|---|
| `OUTPUT_FONT` | 宋体 | 全文字体（中英文同设 `w:eastAsia`）|
| `OUTPUT_SIMPLIFIED` | true | 是否繁→简 |

**硬编码在 `writer/docx_writer.py`（当前改不了）**：
- **字号**：完全未设置，用 python-docx 默认 → 最明显缺口
- **列宽**：完全未设置，Word 自动均分 → 格式最不像原件之处
- 列结构：`_T1_HEADERS/_T1_FIELDS`、`_T2_HEADERS/_T2_FIELDS` 写死
- 标红规则：ONLY_PLM/CHANGED 标红加粗，写死
- 来源标签 `_SOURCE_LABEL`、各级标题文字、`table.style="Table Grid"` 写死
- 纸张/页边距/横纵向：完全未设置

结论：当前"格式保真"仅到**结构层**（表1/表2分开、分组行、来源列、标红），
**字号/列宽/页面设置不受控**。

### 三档方案
**方案 A：扩展配置项（最小改动，建议先做）**
`config.py` 增加并由 writer 读取：
```
OUTPUT_FONT_SIZE=9              # 正文字号(pt)
OUTPUT_HEADER_FONT_SIZE=9       # 表头字号
OUTPUT_TABLE_STYLE=Table Grid
OUTPUT_PAGE_ORIENTATION=landscape   # 关键件表列多，横向更合适
OUTPUT_MARGIN_CM=1.5
OUTPUT_T1_WIDTHS=1,2.5,3,4,3,3,3,3,3,2   # 各列宽(cm)
```
成本低，解决字号+列宽两个最痛点。适合"格式大致规范即可"。

**方案 B：模板文件驱动（推荐，中等成本）**
放 `templates/关键件清单模板.docx`，预置页面设置/表头/列宽/样式；
生成时 `Document("模板.docx")` 打开并**只追加数据行**，继承模板样式。
- 优点：格式由业务用 Word 直接维护，换机型/客户只换模板，不改代码
- 需补：模板占位定位约定（命名书签或固定表格索引）
- 性价比最高的"格式保真"路线

**方案 C：以原始 .doc 为基底改写（保真最高，成本最高）**
Word COM 打开 PLM 原件、在原档标注差异插行，保留 100% 原排版。
- 早期已评估：COM 慢且易悬挂（正因此才改为模板化重建）
- 除非业务要求像素级一致，**不建议**

### 推荐路径
先 A（补字号/列宽/页面方向，立刻改善观感），同时向业务确认是否有标准模板文件；
若有则上 B，把格式交给模板维护。C 暂不考虑。

## 三.46、实现第 2.5 趟"型号集合匹配"（确定性，替代前缀方案）（2026-08-03）

### 背景
型号列常一格罗列多个可选型号，整格字符串比较会把"型号列表扩充"误判为两侧各自独有。
三.41 实验已证明**前缀判据不可取**（依赖书写顺序、误配型号族、收益仅 3 对），
改用**集合关系**判定：确定性、与书写顺序无关、语义可分级。

### 设计（保守落地）
不动 rich/loose 两趟，在 loose 之后加**第 2.5 趟**，约束与 loose 完全一致
（同表 + 同组 + 同关键件名称），仅把型号判据从"整格全等"放宽为集合关系：

| 集合关系 | 处理 |
|---|---|
| equal | 已被 loose 全等捕获 |
| **subset**（真子集，列表扩充/收窄）| → CHANGED，`changed_fields` 标注 `(型号集合：新增 X、Y)`，**自动合并** |
| **overlap**（交集非空、各有独有）| 语义待业务确认 → 判 CHANGED 但标 `pair_reason`（置信度 0.6 < 阈值）**交人工确认**，不擅自决定 |
| disjoint | 不配，各自独有 |

配置化（`rules/data/merge_rules.yaml` → `model_set_match`）：
`enabled` / `separators` / `min_token_len` / `accept_subset` / `accept_overlap`（默认 false）。

### 两个实现难点
1. **`/` 的歧义**：`/` 既是分隔符又是型号内字符（`PC/ABS-5140`）。
   解法：只按**非 `/` 分隔符**切分，避免把 `PC/ABS-5140` 误拆成 `{pc, abs-5140}`。
2. **括号说明被误拆**（首轮测试暴露）：真实型号如
   `HD850K8U61-TBLC*(*代表企业内部代码，由一个或多个空、字母、数字…)`，
   括号内说明被 `、`/`,` 拆成"字母""数字"等**伪型号 token**，
   导致不同型号因共享同一段说明而产生虚假交集（实测多出 1 对噪音候选）。
   解法：新增 `_strip_notes()` 先剥离括号（半/全角）内容再拆分；剥离后为空则退回原文。
   **效果：噪音候选 1 → 0，3 对真实配对不受影响。**

### 改动文件
| 文件 | 变更 |
|---|---|
| `rules/data/merge_rules.yaml` | 新增 `model_set_match` 配置块 |
| `differ/diff_engine.py` | 新增 `_MS_DEFAULTS`、`_strip_notes`、`_split_models`、`_model_set_relation`、`_model_set_desc`；主流程插入第 2.5 趟；docstring 更新 |

### 验证（新增 `tests/test_model_set_match.py`，9 组用例全过）
1. **拆分器** 8 例：型号自带 `/` 不误拆、去空格、`/` 占位符过滤、**括号说明剥离**（半角+全角）
2. **集合关系** 5 例：equal / subset(双向) / overlap / disjoint 判定正确
3. **subset → CHANGED**，`changed_fields` 含 `(型号集合：新增 pc/abs-5143、pc/abs-5144)`，且不标待确认
4. **顺序无关性**：`F-D、F-M` vs `F-D、F-M、F-X` / `F-X、F-M、F-D` / `F-M、F-X、F-D`
   三种书写顺序**均配成 CHANGED**（前缀判据在此会失效）
5. **overlap** → 标 `pair_reason`、置信度 0.6 < 0.8 阈值（交人工）
6. **disjoint** → 各自独有
7. **跨组/跨表仍不配对**（约束未被放宽）
8. **关闭开关** → 完全回退原行为
9. **真实东芝样例**：

  - `frontend/src/pages/WorkspacePage.tsx` 下载接口改用 `apiUrl()`；

- **配置原则**：不修改 FastAPI 的 `/api/v1/*` 路由；不在内层 8123 Nginx 配置增加 `/certagent` 前缀。外层 `location /certagent/ { proxy_pass http://127.0.0.1:8123/; }` 的尾部 `/` 会剥离 `/certagent`，内层继续接收 `/api/...`，也保持直接访问 `:8123` 可用。
