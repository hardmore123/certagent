# CERT/DRAFT 行级并排核对与人工确认闭环

本次改造在既有字段级 `VerifyDiff` 之上生成 `RowDiff`，把 CERT/DRAFT 的匹配结果聚合为 `SAME`、`CHANGED`、`ONLY_CERT` 和 `ONLY_DRAFT`，并通过 `/row-diffs` 和静态页面提供并排复核。正常行级路径中，差异先绑定物理 `row_key`，再把一行操作展开为原有的字段级决策，因此 `finalize_review` 仍可按原平铺 key 集合生成最终文档；`/diffs` 也继续读取同一平铺差异列表。批注写回路径使用 DRAFT 文档和 DRAFT 锚点，认证资料只参与定位与比较。

Watch for: **confirmed** DRAFT 独有安全/EMC 物理表会生成没有任何 `RowDiff` 承接的 `table_extra_in_draft`，使行级页面无法提交完整决策；**confirmed** 页面固定只取前 10,000 个行差异并忽略接口返回的 `total`，大结果也会出现同样的无法闭环。

**Verdict**: NEEDS_CHANGES

## High-level view

普通匹配行、两侧独有行以及产品描述/变更确认的子块级差异会统一回填 `diff_keys`，使行级 verdict 能回到字段级最终化；**confirmed** 未被表级匹配承接的 DRAFT 安全/EMC 物理表仍只存在于平铺差异中。

`/diffs` 保持字段级证据，`/row-diffs` 增加双侧整行值、关系状态和聚合决策；**confirmed** 固定取数上限、未处理的部分提交响应以及可见但不可操作的状态选项，会把后端“必须覆盖全部平铺 key”的约束暴露成界面闭环问题。

两个生产写回入口都以 DRAFT docx 和 DRAFT 锚点为目标，缺少 DRAFT 锚点的差异只进入汇总；输出校验也按 DRAFT 文档检查锚点边界。

### RowDiff 聚合与 `finalize_review` 的 key 契约

字段级比较、整行缺失/新增、表级存在性和可选子块存在性路径都在创建 `VerifyDiff` 时带上 `row_key`。`compare_blocks()` 完成全部比较后才执行 `_bind_diff_keys()`，按该物理 key 把最终已经去重（包括重复差异的后缀 key）的 `VerifyDiff.key` 回填到 `RowDiff.diff_keys`。因此正常情况下，`SAME` 行没有待确认 key，`CHANGED` 行含所有字段不一致 key，`ONLY_CERT`/`ONLY_DRAFT` 行各含一个“整行” key；可承接的表/子块级差异则以 `row_kind="block"` 的 ONLY 行承接。

这层聚合不会改变 `finalize_review` 的输入契约：页面的行级操作只是对该行全部 `diff_keys` 写入同一个 verdict，最终仍提交 `{VerifyDiff.key: decision}`。`finalize_review` 忽略 `RowDiff` 本身，只对 trace 中的平铺 `diffs` 做 known/missing/unknown 集合校验，再把 `accept`/`modify` 的差异交给 DRAFT 批注和汇总生成。现有 19 个 Python 单元测试通过；存量 `runs/row_view_2026-08-28/verification.json` 显示 2,187 个差异、1,088 行、2,187 个唯一承接 key，四类行状态分别为 11/900/165/12。

### DRAFT 独有物理表的承接缺口

**confirmed** `report_verify/verify_differ.py` 的 `_list_block_diffs()` 尾部为每个未分配 DRAFT 表调用 `_table_presence_diff(block_type, draft_block, rules, missing_in_draft=False)`，没有传入当前的 `row_diffs`。该调用仍返回 `table_extra_in_draft` 的 `VerifyDiff`，但不会创建对应的 `RowDiff`；内存测试已经复现 `diffs=[table_extra_in_draft]` 而 `row_diffs=[]`，CERT 没有同类表时也会触发。

这会破坏从界面到最终输出的守恒关系：`/diffs` 和 `job.diff_count` 仍包含该 key，`/row-diffs` 却没有它，`reviewableKeys()` 也不会把它提交给后端；即使所有可见行都已确认，`finalize_review` 仍会因缺少该 key 而拒绝生成最终文件。修复应让这条表级差异也生成 `RowDiff(row_kind="block")`，并覆盖“CERT 无该 block”“表级候选低于阈值”“DRAFT 有未分配物理表”三类场景。

### `/diffs`、`/row-diffs` 与提交状态

`/diffs` 仍从 `result.diffs` 分页，并在每个原有差异上叠加当前 verdict/note，没有把字段级证据改成行级摘要；这一兼容路径可继续供旧客户端消费。`/row-diffs` 返回完整的 CERT/DRAFT 行值、物理引用、变化字段、匹配信息和 `diff_keys`，再按该行 key 集合计算 `unreviewed`、`partial` 或统一 verdict，这与行级操作的映射关系一致。

**confirmed** 前端 `loadRowDiffs()` 固定请求 `limit=10000`，而 API 允许返回 `total` 和 `offset`；页面没有在 `items.length < total` 时继续请求，也没有在提交前比较服务端总 key 数。超过 10,000 个 RowDiff 的报告会被截掉，页面可能显示全部已确认，但后端的平铺差异仍未全部决策。

**confirmed** `submit_decisions()` 以 `len(job.decisions)` 和平铺 diff 数量作提前判断，并允许未知 key 先写入 job；只有达到数量阈值后，`finalize_review()` 才报告 unknown/missing。前端提交 handler 只在响应 `status === "done"` 时更新页面，API 返回仍为 `review` 的合法部分结果不会刷新计数、重新加载行或显示缺失 key，因而会停在“正在生成最终双文档…”。服务端应先按 trace 的 known keys 拒绝 unknown 并返回 missing，前端按响应重新同步，而不是用对象数量近似集合相等。

### 并排行视图的筛选、展开和行级决策

在已加载的记录范围内，待确认筛选和“下一个待确认”都依据聚合状态工作，展开状态只改变字段展示；每个 accept/modify/ignore 行操作都遍历该行全部 `diff_keys`，所以一行含多个字段差异时不会漏掉其中某个 field-level decision。

**confirmed** 输入审批说明的 change handler 在当前行 verdict 不是 accept/modify/ignore 时强制使用 `accept`，所以对尚未裁决的行只填写说明并离开输入框，就会把全部字段差异标成 accept。**confirmed** 页面还把 `partial` 和 `unreviewed` 渲染为 select 选项，但 change handler 对这两个值不调用 `setRowDecision`；用户选择它们后状态可能保持旧值，选项与实际状态机不一致。两者都应改成显式、可预测的决策操作。

### 批注目标仍是 DRAFT

`run_verification()` 和 `finalize_review()` 都把 `draft_docx` 传给 `write_comments()`；`VerifyDiff.draft_anchor` 由 DRAFT 行的 table/row/cell 锚点产生，CERT 侧只保留文本值和位置说明。缺失 DRAFT 行或缺失子块的差异没有可写锚点，会留在汇总中；有 DRAFT 行的字段差异和 DRAFT 独有行才可能写入 DRAFT。`validate_outputs()` 还用同一 DRAFT 文档验证锚点范围，存量行级产物的 consistency 记录为 `draft_is_comment_target: true`，其批注 XML 可读取。

### 覆盖缺口

**confirmed** 现有测试覆盖了普通 SAME/CHANGED、两侧独有行、子块缺失、API 决策状态和最终化，但没有覆盖 DRAFT 独有物理表、超过 API 上限的分页、非 `done` 提交响应或浏览器端输入/筛选行为；静态 `index.html` 没有对应的浏览器测试。提交前至少应增加表级 RowDiff 守恒断言、完整 key 集合的 API 测试，以及对行操作和分页的前端测试。
