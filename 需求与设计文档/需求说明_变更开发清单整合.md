# 需求说明：变更-开发 关键件清单整合

> 来源：《20.认证智能体PRD》→ 准备认证资料 → 产品认证 → CCC认证 → 变更-开发
> 定位：认证智能体"清单对比"能力的**第一个接入口**（MVP）
> 编写依据：PRD 正文 + 工作区真实样例文件结构解析

---

## 一、功能定位

新机型做"变更认证"时，需要把 **PLM 系统新生成的关键件清单** 与 **派生所选原证书的原报告清单** 两份文件整合成一份"变更后的关键件清单"，并生成一份"变更前后对照表"，作为认证变更流程（KOA 3C 认证变更流程）的提交材料。

现状是各专业工程师人工比对、手工合并、手工标注，耗时且易漏。本功能用 Agent 自动完成整合与对照表生成，人工只做确认。

---

## 二、角色与场景

- **角色**：电路工程师、电源工程师、模组光学工程师、结构工程师、认定工程师
- **场景**：各专业对比原报告，整合输出变更后的关键件清单
- **触发**：工程师上传两份 Word 清单文件，点击"整合"

---

## 三、输入 / 输出

### 输入（2 个 Word 文件）

| 文件 | 角色 | 样例 |
|---|---|---|
| PLM 导出清单 | 本次新机型 PLM 生成的清单（**变更后来源**） | `75U66Q(01)_PLM导出清单.doc` |
| 原报告清单 | 派生所选原证书的原报告清单（**变更前基准**） | `75U66Q(01)_原报告清单.doc` |

### 输出（2 个 Word 文件）

| 文件 | 内容 | 样例 |
|---|---|---|
| 汇总版关键件清单 | 两份整合后的完整清单：重复项合并，新增/差异项**标红加粗**并备注来源 | `75U66Q(01)_安全&EMC关键件清单.doc` |
| 变更前后对照表 | 3 列表格，按业务项归纳变更内容 | `75U66N变更前后对照表.doc` |

---

## 四、输入文件真实结构（解析样例得出）

两份输入清单结构一致，均含 **2 张表**：

### 表1 — 关键件主清单（10 列）
`序号 | 位号 | 部件号 | 关键件名称 | 型号 | 规格/材料 | 生产者(制造商) | 生产企业 | 认证标准 | 备注(证书号)`

结构特征（实现时必须处理）：
1. **分组标题行**：如"以下部分适用于整机结构1，I类电源线、器具耦合器结构"，跨列合并，用于分段，需保留。
2. **跨行合并**：`序号`/`关键件名称` 只在该件首行出现，后续行为空表示"同一关键件的延续"。
3. **一格多型号**：`型号` 单元格内常用顿号/逗号分隔多个型号（多个备选或多张证书对应），比对时可能需拆分。
4. `备注` 列实际存放**认证证书号**（如 2007010101232657）。

### 表2 — 备选件/电源单元清单（10 列）
`序号 | 位号 | 元件 | 名称 | 型号 | 规格/材料 | 制造商(全称) | 生产厂(全称) | 本次使用/备用 | 备注`

结构特征：
- `本次使用/备用` 标记该件是否本次使用。
- `备注` 列存放"对应 XX、XX 机型"信息。

### 对照表 — 输出模板（3 列）
`变更项目 | 变更前 | 变更后`

样例变更项（业务归类，非逐行 diff）：
1. 增加产品型号规格
2. 增加机内电源单元备选件
3. 增加主板（含网卡/调谐单元/天线隔离器）备选件
4. 增加液晶屏（含 LCD 控制电路）备选件
5. 补充安全&EMC关键件清单中供应商信息
6. 增加整机外观、内部结构、铭牌等照片

"变更前"多为"见原报告"；"变更后"为"见原报告 增加：<具体型号/规格/生产企业/制造商/备注>"。

---

## 五、整合规则（核心）

PRD 原文："重复资料合并，非重复资料整合并标红加粗，备注资料来源自哪份文件"。细化如下：

### 5.1 比对粒度
以"行级报备项"为单位（表1、表2 各自独立比对）。同一关键件下的每一行（一个具体型号项）是一个比对单元。

### 5.2 比对匹配键（2026-07-27 已确认）

本 MVP 将**分组 `group` 视为关键件身份的一部分**，不同机内电源单元分组下的同名同型号器件不得跨组匹配。

- **表1 rich key**：`表号 + 分组 + 关键件名称 + 型号 + 位号 + 规格/材料 + 证书号(备注)`；
- **表1 loose key**：`表号 + 分组 + 关键件名称 + 型号`，仅用于同一分组内判断“内容变更”，不允许跨分组匹配；
- **表2**：同样保留表号和分组上下文，按行级多重集对齐；
- rich/loose 索引的值必须使用列表，配合已消费行集合逐条匹配，不能使用会覆盖重复项的单值字典。

业务保留规则：

1. 同名同型号但证书号不同，必须分别保留多行；
2. 同名同型号但位号不同，必须分别保留多行；
3. 原报告中未被匹配消费的行全部保留，并标记来源“原报告”；
4. 两侧均有且 rich key 一致的行合并为一行；
5. 同一分组下 loose key 命中但 rich key 不同的行，按一对一行级差异输出，不折叠物理行。

比对前继续做归一化：去除多余空格、全/半角统一、繁简统一、单位符号统一（如 `～`/`~`）。

> 说明：旧版本只使用 `关键件名称 + 型号` 作为 loose key，会把不同分组的同名同型号器件错误合并；2026-07-27 已在 `compare_core/differ/diff_engine.py` 修正。

### 5.3 合并逻辑
| 情形 | 处理 |
|---|---|
| 两份都有且匹配键一致（重复） | 合并保留一份，不标注 |
| 仅原报告清单有 | 保留，标注来源"原报告" |
| 仅 PLM 导出清单有（新增项） | 保留，**标红加粗**，标注来源"PLM导出" |
| 两份都有但内容不同（如规格/证书号有差异） | 保留并**标红加粗差异字段**，备注两份来源 |

### 5.4 标注规范（待确认具体格式，见第八节）
- 新增/差异内容：字体标红 + 加粗
- 来源备注：写入 `备注` 列或新增"资料来源"列
- 保留原表的分组标题行与关键件分组结构

---

## 六、变更前后对照表生成规则

对照表**不是逐行 diff 的堆砌**，而是把行级差异**归纳为业务变更项**：

1. 将 5.3 得到的"新增/差异项"按关键件类别聚合（电源单元、主板、液晶屏、供应商信息…）。
2. 每类生成一条变更项，`变更前` 填"见原报告"，`变更后` 填"见原报告 增加：<归纳后的新增内容>"。
3. **照片类变更**（外观/内部结构/铭牌照片）无法从两份清单推出，需人工补充或作为固定条目提示（见第八节）。

这一步的"语义归纳"是 **Agent(LLM)** 的职责；行级 diff 由代码完成以保证确定性。

---

## 七、Agent / 系统分工（借助 Agent 实现）

遵循"能用代码保证确定性就不交给模型"的原则，LLM 只做语义归纳与判断：

```
[上传两份 .doc]
      │
1. 解析模块(代码)   .doc → 结构化行(表1/表2/分组行)，处理跨行合并、一格多型号
      │
2. 对齐/Diff 引擎(代码)  按匹配键归一化对齐 → 输出: 重复 / 仅原报告 / 仅PLM / 内容差异
      │
      ├─3a. 合并生成(代码)   汇总清单.docx：合并去重 + 新增差异标红加粗 + 备注来源
      │
      └─3b. 变更归纳 Agent(LLM)  行级diff → 归纳为业务变更项 → 变更前后对照表.docx
      │
4. 写回(代码)   输出两份 Word 文件
      │
5. 人工确认 → (后续)反馈沉淀规则
```

Agent 使用点：
- **变更归纳 Agent**：输入结构化 diff，输出对照表的"变更项目/变更前/变更后"。
- （可选）**匹配辅助 Agent**：当型号/规格文本差异较大、代码难判定是否"同一项"时，由 LLM 辅助判断相似度。

## 八、待业务确认的问题（Open Questions）

1. **变更方向**：确认"原报告清单=变更前基准，PLM导出清单=变更后"是否正确？（对照表方向依赖此项）
2. **匹配键**：✅ 本 MVP 已确认表号/分组属于身份上下文；表1 rich key 为“分组+关键件名称+型号+位号+规格/材料+证书号”，loose key 为“分组+关键件名称+型号”；同名同型号不同证书号或位号必须按多行保留。后续仍需确认表2是否有更细的业务身份字段。
3. **一格多型号**：`型号`单元格内多型号是否需要拆分为独立比对项，还是整格比对。
4. **"重复"判定口径**：完全字符相同，还是归一化后相同（空格/全半角/单位/换行）。
5. **标注格式**：标红加粗的确切样式；来源备注写入现有`备注`列还是新增列；差异是否加 Word 批注。
6. **对照表变更项分类**：是否有固定的变更项模板/顺序；分类粒度（按关键件名称 or 业务类别）。
7. **表2 的"本次使用/备用"**：备用件是否参与整合与标注。
8. **照片类变更**：清单中无照片信息，此类变更项如何生成（固定占位提示 / 人工补充 / 额外输入）。
9. **文件格式**：输入统一为 `.doc` 还是也可能 `.docx`；输出格式与命名规范（是否带时间戳）。
10. **准确性口径**：PRD 非功能要求"准确性 100%、≤50s"，需确认 LLM 环节采用"宁可多标不漏标 + 人工确认"的兜底策略。

---

## 九、验收标准

- 输出符合样例格式的 2 份 Word：汇总关键件清单 + 变更前后对照表。
- 重复项正确合并、新增/差异项正确标红加粗并备注来源。
- 对照表变更项归纳准确、可读，供审批人确认。
- 用现有样例（75U66Q 一组）跑通并与样例输出比对回归。
- 参考 PRD 价值指标：减少各专业反复线下沟通，提升整合效率。

---

## 十、技术要点与风险

- **.doc(老二进制) 解析**：本机 Python 3.14 + Word COM(pywin32) 可解析；无 Word 环境需 LibreOffice/转 docx 方案。解析准确率是第一关卡。
- **Word 写回**：需支持单元格内富文本标红加粗、保留复杂表格（合并单元格、分组行）。
- **一格多型号 / 跨行合并** 是解析与比对的主要难点。
- 可复用参考项目 `pdf-reviewer` 的差异汇总、标注、反馈学习闭环思路（其为 PDF 版面审查，需新增"结构化清单对齐"层）。
