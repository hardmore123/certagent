# 认证智能体项目经验总结

> 总结范围：2026-07-17 至 2026-08-21 的需求分析、解析器、清单整合、组级归纳、长期记忆、报告草稿核对和生产部署实践。
> 适用对象：后续开发、需求评审、业务验收、生产运维和类似文档智能化项目。

## 一、结论先行

认证智能体的核心不是“让大模型直接读 Word 并生成结果”，而是建立一条可追溯的数据链：

`Word 输入 → 结构化解析 → 归一化 → 规则/多重集比对 → 业务组级抽象 → LLM 归纳建议 → 人工确认 → Word 输出 → 反馈记忆`

项目已经验证的关键原则如下：

1. **先结构化，后智能化**：Word 表格的合并单元格、分组标题、表号和列位必须先被可靠解析，否则后面的差异判断和 LLM 归纳都建立在错误数据上。
2. **数据正确性优先于模型能力**：行丢失、跨分组误匹配等问题不能靠 Prompt 修复，必须在解析和比对层解决。
3. **行级比对与业务级归纳分层**：行级 diff 负责完整保留数据和精确标注；关键件组级 diff 负责表达“换型、整组新增、整组减少、供应商替换”等业务动作。
4. **LLM 负责语义表达，不负责事实凭空生成**：事实来自解析结果和规则，LLM 只做分类、归纳和建议；照片、额外型号等输入外信息必须标为外部输入或人工补充。
5. **人机闭环比一次性自动化更可靠**：差异需要人工确认，确认理由要落盘，并通过指纹聚合反哺后续建议。
6. **验收必须基于真实差异样例和明确业务口径**：同基线样例只能验证流程，不能验证变更识别准确率。
## 二、需求分析与范围控制

### 1. 先把大 PRD 拆成可验收的 MVP

认证业务包含对比、抓取、生成、归档、查询等多类能力，首个落地点选择“变更-开发关键件清单整合”是正确的：输入和输出边界明确，能够形成“解析—判断—建议—确认—生成—记忆”的完整闭环。

可复用的方法是：

- 先建立任务全景，区分当前 MVP、后续能力和外部系统依赖；
- 为每个需求写明输入、输出、人工节点、验收口径和待业务确认项；
- 不把 PLM、SCP、云盘、档案室、认证网站等外部接口提前耦合进核心引擎；
- 对无法从输入推导的信息（照片、额外型号、人工补录）显式设计额外输入入口。

### 2. 业务期望输出不一定是输入的机械并集

东芝 85ZXSF 样例表明，业务期望清单包含字段改写、结构调整和输入之外的人工补录。业务期望 223/9 行，而 Demo 理论输出 216/9 行，并不代表 writer 漏写；其中部分记录能按名称和型号追溯，但证书、分组、供应商等字段已被业务重新整理，另有型号在两份输入中完全不存在。

因此验收时必须把差异分成：

- 输入可确定且系统应识别；
- 输入可追溯但业务做了字段改写；
- 输入之外的人工补录或其他资料来源；
- 业务规则尚未定义，不能由代码猜测。

## 三、Word 解析经验

### 1. 真实 Word 比简单 fixture 难得多

真实 `.doc/.docx` 中出现过：整行合并的分组标题、纵向合并、横向合并、合并后列号左移、跨行填充、非法控制字符、表1/表2 混排以及表头命名变体。解析器必须按真实文档结构处理，不能只依赖规则整齐的测试表。

已验证的处理策略：

- 分组标题行按整行合并特征识别，写入 `group`，不当作数据行；
- 对 COM 表格优先使用 `Range.Cells` 和真实行列号，避免直接遍历 `Rows(r).Cells` 导致纵向合并表格丢失；
- 对横向合并记录合并点，按实际列号回填，防止型号、规格和制造商整体错位；
- 对纵向合并做前值恢复，但保留源文档空值语义；
- 解析层和写回层都清洗 XML 非法控制字符；
- 表头采用归一化和别名映射，兼容全角括号、空格、繁简体及“规格/规格材料”等变体；
- `.doc` 转换与解析解耦，生产环境优先预转换为 `.docx`，避免批量 COM 长时间悬挂。

### 2. 解析质量要量化，不只看“能打开”

75U66Q 两份样例均解析出 475 行（表1 438、表2 37），关键字段填充率达到 100%，跨行填充失败为 0，列错位征兆为 0。东芝样例 docx 路线解析出原始 159 行、PLM 175 行，主要字段达到 99%—100%。

但“字段填充率高”不等于“业务准确率高”。还应分别统计：总行数、分表行数、分组事件、关键字段填充率、异常行、严格指纹匹配、多重集差异和人工金标准覆盖率。COM、docx 转换和视觉路线的失败状态也要单独记录，不能把“缺少配置”或“调用被阻断”计入解析失败率。
## 四、比对与匹配经验

### 1. 匹配键必须表达“物理行身份”和“内容变化”

早期仅用“关键件名称+型号”作为字典键，导致 438 行被折叠为 175 个唯一键，丢失 263 行。根因不是 Word 输出，而是比对层用 `setdefault` 把重复行覆盖了。

正确做法是分开设计：

- **rich key**：表号 + 分组 + 名称 + 型号 + 位号 + 规格材料 + 证书号，用于判断是否为同一物理行；
- **loose key**：表号 + 分组 + 名称 + 型号，用于判断同一业务件的内容是否发生变化；
- 使用列表和 `used` 集合逐条消费，不能用单值字典覆盖重复项；
- PLM 侧作为变更后基底，原报告未消费行全部追加为 `ONLY_ORIG`；
- 同名同型号但分组、证书号或位号不同，必须保留多行。

### 2. 分组是关键业务上下文

将 `group` 纳入匹配键后，东芝样例从 196 行理论输出增加到 216 行，跨分组误合并明显减少。`X 电容`、`Y 电容`、压敏电阻和泄放电阻等重复物料在不同机内电源单元分组下都能分别保留。

经验是：当同名同型号在多个产品结构、机型或分组下出现时，分组不是展示字段，而是身份字段。业务确认的匹配规则应写入需求文档和回归基线，不应只留在代码实现中。

### 3. 不要让 writer 决定数据是否存在

输出层应“按 diff 逐行输出”，而不是重新按名称去重。diff 负责判断 SAME、CHANGED、ONLY_ORIG、ONLY_PLM；writer 负责保留全部数据、表1/表2、分组标题、来源和红色标识。这样可以把“数据完整性”和“展示格式”分离，便于定位问题。

## 五、从行级差异到组级业务语义

物理行 diff 适合回答“哪一行不同”，不适合直接回答“这次业务发生了什么”。东芝样例中，旧电源单元的多个子件整组消失、新电源单元的多个子件整组增加，行级结果会产生大量独有项；按 `(表号, 分组, 关键件名称)` 聚合后，43 个组可归纳为 SAME、REPLACED、SHRUNK、ONLY_ORIG、ONLY_PLM 等状态。

只读实验得到两条重要证据：

- 业务期望中 41 条严格未覆盖行，有 40 条落在非 SAME 组，组级视角覆盖了 97.5% 的业务动作；
- 组级 Mock 从 22 条行级归纳压缩为 5 条业务模板，业务模板覆盖从 2/5 提升到 5/5。

因此推荐“双层 diff”架构：

- 行级 diff：完整性、逐字段变更、红色标注、人工决策和输出回溯；
- 组级 diff：换型、整组新增/减少、选型集合变化、供应商变更等业务归纳；
- `GroupDiff.diff_keys` 保存从组回溯到物理行的关系，保证可解释性。

## 六、LLM 使用经验

### 1. 先把数据 shape 做对，再优化 Prompt

DeepSeek V4 Flash 和 Pro 在组级输入上都达到业务模板 5/5 覆盖；Pro 没有自动解决“供应商信息”分类边界过宽的问题，说明该问题是业务定义不清，而不是模型能力不足。

有效 Prompt 约束包括：

- 输出条目数固定为业务模板数量；
- 每个非 SAME 组必须被某个条目覆盖；
- 无对应组时输出“本次无相关组变更”；
- 照片等输入外信息固定输出 `[外部输入]` 占位；
- 输出前进行条目数和组覆盖自检；
- 使用结构化 JSON，解析失败回退 Mock 或人工确认。

### 2. 真正的事实边界必须由系统控制

LLM 可以把“原始组、PLM 组、共同选型、仅一侧选型”组织成业务语言，但不能凭空补充照片、产品型号或供应商结论。凡是输入没有的数据，应进入 `manual_supplements` 或额外资料入口，并在结果中标明来源。

当前建议默认使用成本更低、速度更快的 Flash；Pro 作为复杂样例或最终润色备选，不以更换模型代替业务规则确认。
## 七、人工确认、长期记忆与 Web 化经验

### 1. 人工确认是业务闭环，不是异常分支

系统已实现差异确认、独有项手动匹配、相同/拆分判断和 AI 配对拒绝等分类裁决。建议保持明确的 verdict 语义：`accept`、`reject`、`reject_dup`、`reject_pair`、`reject_same`、`reject_split`、`unpair`，避免用一个布尔值承载不同业务含义。

### 2. 记忆必须“写入 + 读取”同时成立

反馈采用 JSONL 追加写，每条记录保存时间、差异键、裁决、理由、指纹和上下文。指纹应跨任务稳定，例如 `diff类型|归一化件名|归一化型号`，系统按指纹聚合历史确认与否决次数，再改变建议置信度或预置忽略。

仅写不读不构成学习闭环；仅按内部行号记忆也无法跨任务复用。长期记忆应放在 git 追踪或明确归档的位置，不能只放在临时 `runs/` 目录，以免服务器重启、部署覆盖或清理运行目录导致丢失。

### 3. Web 生产化要关注进程环境，而不只是代码

**CertAgent 生产访问地址：** http://10.18.87.51/certagent/

部署过程中暴露出的典型问题包括 nginx ACL、systemd 缺失 HOME、环境变量未加载、端口不一致、加密文件上传和旧格式文档转换不可靠。经验如下：

- systemd 服务显式设置 `HOME`、工作目录和 `.env` 加载路径；
- 生产端口、反向代理前缀和前端 Vite `base` 必须统一；
- 通过构建产物中的 script、stylesheet、favicon 路径和实际 HTTP 响应做部署冒烟；
- 透明加密文件、Word 密码加密文件和旧 `.doc` 要区分处理，不要把三种问题混为一个上传错误；
- 对 `.doc` 转换设置超时、失败提示和明确的替代流程；
- 统计 API 用户、接口、耗时和状态码，但不向普通用户暴露后台统计。

生产检查不能只看首页是否能打开，还应至少验证：登录、上传、解析、AI 配对、确认提交、产物下载和记忆落盘。

## 八、报告草稿准确性核对的复用经验

报告草稿核对与清单整合的共同底座是解析、归一化、差异模型和人工确认，但不能把完整报告当成一张普通表。报告包含多张混合表，需要先用表头指纹定位安全关键件表、EMC 表和变更确认表，再进行异类字段映射。

推荐实现顺序：

1. 先做批注写入 PoC，确认差异能定位到报告中的表格单元格；
2. 新建报告解析层，记录表索引、行号、单元格和段落锚点；
3. 扩展字段别名和列映射，复用现有清单解析与归一化；
4. 复用差异模型，但按“报告核对”语义输出 A 值、B 值、差异类型和建议；
5. 生成批注版报告和编号汇总文档；
6. 再接入 Web 任务、审批循环和二次核对。

批注定位失败时，应退化到单元格首段批注，并在汇总文档中保底列出，原则是“不漏差异”优先于“每次都精确到字符”。

## 九、验证与验收方法

建议每次迭代固定保留三层验证：

### 1. 单元/冒烟验证

覆盖归一化、分组识别、合并单元格、重复行、多表输出、繁简转换、红色标注和 JSONL 记忆写入。现有 smoke 已验证 SAME、CHANGED、ONLY_ORIG、ONLY_PLM 以及 LangGraph interrupt/resume。

### 2. 真实文件回归

至少使用一份同基线样例验证“不丢行、不乱列、不破坏结构”，再使用一份真实有差异样例验证变更分类、标红、对照表和人工决策。不能用只有 SAME 的样例宣布差异识别准确。

### 3. 业务金标准验收

对业务期望逐行标注“可由输入确定、可追溯但字段改写、输入外补录、规则待确认”，分别统计行级召回、字段级一致、组级动作覆盖、对照表分类准确率和外部信息识别率。不要把字符串命中率或 Demo 输出行数直接称为准确率。

每次发布都应保留输入快照、结构化 JSON、diff、组级 payload、LLM prompt/响应摘要、人工决策、输出文件和运行日志，形成可回放证据链。

## 十、已验证的失败模式与改进顺序

| 失败模式 | 根因 | 改进经验 |
|---|---|---|
| 大量行消失 | 名称+型号单值字典覆盖重复行 | 行级多重集 + `used` 集合，输出不去重 |
| 跨分组错误合并 | 匹配键缺少 group | 将表号、分组纳入身份上下文 |
| 输出表被拍平 | writer 固定 8 列 | 表1/表2独立、保留分组、来源和标注 |
| 繁简混排 | 只有全半角归一化 | 匹配与输出均增加繁转简，且可配置 |
| Mock 对照表过碎 | 直接对物理行做业务归纳 | 使用组级 diff，再交给 LLM 表达 |
| LLM 分类边界不稳定 | 业务类别定义模糊 | 先确认类别边界，再改 Prompt/规则 |
| 记忆不生效 | 只写不读或环境变量未加载 | 进程启动加载配置，按稳定 sig 聚合读回 |
| 生产 AI 不生效 | systemd 没有 LLM 环境变量 | `.env` 自动加载 + 启动时配置检查 |
| `.doc` 批量卡死 | COM/转换链路不稳定 | 预转换、超时、串行队列、失败可重试 |

推荐修复顺序始终是：**数据不丢失 → 匹配身份正确 → 输出结构正确 → 业务组级归纳 → LLM 表达优化 → 体验和性能优化**。

## 十二、可复制的项目方法论

面对类似“业务人员拿两份复杂文档做核对”的任务，建议固定采用以下流程：

1. **先做样本盘点**：列出文档类型、表数量、字段、合并方式、期望输出和人工补充信息。
2. **先做解析基线**：输出结构化 JSON 和质量报告，不急于接 LLM。
3. **先解决数据完整性**：任何丢行、错列、错误去重都优先修复。
4. **定义业务身份键**：把表号、分组、位号、证书号等上下文写成明确规则。
5. **同时保留行级和组级结果**：前者保证证据，后者支撑业务语言。
6. **让 LLM 只处理受控 payload**：固定 JSON schema、类别、覆盖约束和外部输入标识。
7. **保留人工确认和理由**：把裁决转为稳定指纹，形成可查询、可归档的记忆。
8. **按真实差异验收**：同基线只验证回归，不代表变更准确率。
9. **最后再做部署和体验优化**：路径、权限、进程环境、转换失败和下载链路必须纳入生产验收。

> 最重要的经验：复杂文档智能化项目的质量上限，首先取决于结构化数据和业务规则的清晰度，其次才取决于模型本身。
