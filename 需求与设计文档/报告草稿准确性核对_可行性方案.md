# 报告草稿准确性核对 — 可行性方案

> 对应需求：**5. 确认报告草稿准确性**
> 场景：核对认证机构出具的**报告草稿**是否与海信提供的**认证资料**一致，输出差异项，用两种方式标识（① 报告草稿内以 Word 批注标注；② 差异项按 1、2、3 汇总供审批人确认）。
> 结论先行：**技术可行，可在现有 `list-merge-demo` 代码资产上扩展实现**，核心难点（报告结构解析、异类比对、批注写入）均有明确落地路径。

---

## 一、需求拆解

| 编号 | 需求点 | 说明 |
|---|---|---|
| R1 | 自动比对两侧文件信息是否一致 | A=海信认证资料（关键件清单等）；B=认证机构报告草稿 |
| R2 | 输出差异点结果 | 明确"哪一项、A 是什么、B 是什么、差异类型" |
| R3 | 标识方式①：报告草稿内**批注**标注差异项 | 在 B 文档差异位置插入 Word 批注 |
| R4 | 标识方式②：**汇总**所有差异项，按 1、2、3 顺序写明 | 供审批人确认，生成独立汇总文档 |
| R5 | 支撑多轮审批闭环 | 草稿→审批→汇总修改项→发机构修改→二次审批，循环至完成 |

---

## 二、两侧样本结构（已实测）

**A｜海信认证资料**（`100E7S-PRO(01)_安全&EMC关键件清单.doc`）
- 表0：安全关键件清单，852 行 × 10 列（序号/位号/部件号/关键件名称/型号/规格材料/生产者(制造商)/生产企业/认证标准/备注）
- 表1：EMC 关键件清单，94 行 × 10 列
- 结构与现有项目输入**同类**，`docx_parser` 基本可直接解析

**B｜认证机构报告草稿**（`A2026...安全描述+EMC.docx`）
- 完整 CCC 试验报告，**29 张表**，混合结构：
  - 首页/报告组成表/**变更确认表**（表3：序号和名称 / 变更前 / 变更后）
  - 产品描述报告、安全描述报告
  - **安全关键件清单**（表6：465 行 × 11 列；表19：534 行 × 10 列，多"部件号"、认证标准可能占两列）
  - 大量样品照片页、EMC 关键件清单、声明页
- 关键件清单是其**内嵌子块**，列结构与 A 不完全一致（列数/列名有别）

> 核心工程差异：**两侧文档异类**（纯清单 vs 报告超集），且 B 中同类信息分散在多张表里，需先"定位再比对"。

## 三、技术可行性分析（四个关键难点）

### 难点 1：报告草稿的结构化解析 —— ★可行
- B 是 29 表混合结构，需从中**识别并抽取目标区块**：安全关键件清单、EMC 清单、变更确认表、产品描述关键字段。
- 方案：新增 `report_parser`，基于**表头指纹**（如首行含"序号/关键件名称/型号/认证标准"→ 关键件清单；含"序号和名称/变更前/变更后"→ 变更确认表）做**表分类路由**，命中后复用现有 `_parse_table` 逻辑。
- 现有 `docx_parser` 已处理 gridSpan/vMerge/跨行填充/分组标题，可直接复用；只需补"多表分类"外层。

### 难点 2：异类字段对齐 —— ★可行
- A 与 B 的清单列名/列数不同（如 A 10 列 vs B 11 列，"生产者(制造商)"表述差异、认证标准合并列）。
- 现有 `HEADER_MAP` + 归一化机制已支持表头别名映射，扩展映射表即可覆盖 B 的列名变体。
- 比对内核（`differ`：归一化→匹配键对齐→差异分类→置信度）**逻辑通用**，可直接复用；仅需针对"核对"语义调整匹配键与字段权重。

### 难点 3：Word 批注写入（R3，最关键）—— ★可行且成本低
- **实测确认**：当前环境 `python-docx 1.2.0` **原生支持** `Document.add_comment(runs, text, author, initials)`，可在指定 run 区间锚定批注。
- 意味着**无需 Word COM / 无需手改 OOXML** 即可给报告草稿打批注，纯 Python、线程安全，可直接在 Web 异步任务里跑。
- 定位策略：解析 B 时为每个清单行/字段记录其所在 `table 索引 + 行号 + 单元格 paragraph`，比对命中差异后回到对应单元格段落的 runs 上 `add_comment`。
- 兜底：若某差异无法精确锚定到 run，则退化为"在该单元格首段落打批注"或在汇总文档中列出，保证不漏项。

### 难点 4：差异汇总文档（R4）—— ★可行
- 输出一份独立文档，按 1、2、3 编号列出全部差异项（差异项 / A 内容 / B 内容 / 类型 / 建议）。
- 与现有 `writer` 生成"变更前后对照表"的能力高度相似，可改造复用。

## 四、现有资产复用评估

| 模块 | 复用度 | 说明 |
|---|---|---|
| `parser/converter`（.doc→.docx） | 直接复用 | A 是 .doc，需先转换 |
| `parser/docx_parser`（表格解析） | 高度复用 | 抽出 `_parse_table` 供报告解析器调用 |
| `differ`（对齐/分类/置信度） | 高度复用 | 核对场景微调匹配键 |
| `rules`（正/反向规则、误报防护） | 复用 | 减少"无意义差异"（空格/全半角/单位写法） |
| `webapi` + `frontend`（任务/确认/下载框架） | 复用 | 新增"核对任务"类型与确认页 |
| `writer`（生成 docx） | 部分复用 | 汇总文档复用；批注写入为新增 |
| `models`（Row/DiffItem/...） | 扩展 | 新增报告区块模型与批注锚点字段 |

**需新建：** `report_parser`（报告结构解析）、`comment_writer`（批注写入）、核对专用 `diff` 语义与字段映射、审批循环状态机。

## 五、目标架构（在现有分层内扩展）

```
输入 A(海信清单.doc) ──┐
                        ├─► 解析归一化 ──► 核对比对(differ) ──► 差异集
输入 B(报告草稿.docx) ──┘        (report_parser 定位子块)
                                                     │
                        ┌────────────────────────────┼────────────────────────────┐
                        ▼                             ▼                            ▼
              ① 批注版报告草稿.docx          ② 差异汇总.docx(1/2/3)         人工确认页(Web)
              (comment_writer)              (writer 改造)                 (复用 review 框架)
                                                     │
                                              审批循环状态机(R5)
```

## 六、批注写入最小验证（技术预研，建议第一步做）

用 10~20 行伪造清单 + 一份精简报告，验证以下链路端到端跑通：
1. 解析 B → 定位安全清单表 → 记录每行单元格段落锚点；
2. 与 A 比对得到差异（构造几处已知差异）；
3. 对差异单元格 `add_comment` 写批注，另存 `批注版.docx`；
4. Word 打开确认批注位置正确、可见、作者/内容正确。

> 该 PoC 成本约 0.5~1 人日，是整个方案唯一有不确定性的环节，优先打通即可锁定可行性。

## 七、分阶段实施计划

| 阶段 | 目标 | 交付 | 预估 |
|---|---|---|---|
| P0 预研 | 批注写入 PoC | 批注版 docx 跑通 | 0.5~1 天 |
| P1 解析 | 报告草稿结构解析 | `report_parser` + 表分类 | 2~3 天 |
| P2 比对 | 异类字段映射 + 核对 diff | 差异集（含类型/两侧内容） | 2~3 天 |
| P3 输出 | 批注版报告 + 差异汇总(1/2/3) | 两份输出文档 | 2~3 天 |
| P4 接入 | Web 任务/确认页/下载 | 端到端可用 | 2~3 天 |
| P5 闭环 | 多轮审批状态机(R5) | 循环流程 + 记忆 | 3~5 天 |

> 前 4 阶段（P0~P4）即可交付"上传两份文件→出批注版+汇总"的可用闭环，约 **9~13 人日**。

## 八、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 报告模板多样，表结构不稳定 | 中 | 表头指纹 + 兜底"未识别区块"提示，逐步积累模板库 |
| 批注 run 锚点定位不准 | 中 | 退化为单元格首段批注 + 汇总文档兜底，不漏项 |
| A/B 列名差异导致字段错位 | 中 | 扩展 `HEADER_MAP`，人工确认页可纠正 |
| "无意义差异"噪声（空格/全半角/单位） | 中 | 复用现有归一化 + 反向规则库 |
| 大表性能（500+ 行 × 多表） | 低 | 纯 Python 解析已验证可承受，必要时按表并行 |
| .doc 转换依赖 Word/LibreOffice | 低 | 现有 converter 已具备双通道容错 |

## 九、结论

1. **整体可行**：比对内核、解析基座、Web 框架均可从 `list-merge-demo` 复用，避免从零开始。
2. **关键技术已验证**：Word 批注写入在 `python-docx 1.2.0` 原生支持，纯 Python 即可实现，是本方案最大的不确定点，且已确认可行。
3. **最大工程差异**：两侧文档**异类**（清单 vs 完整报告），核心新增工作是"报告结构解析 + 批注写入 + 审批循环"。
4. **建议路径**：先做 P0 批注 PoC 锁定可行性，再按 P1~P4 交付可用闭环，P5 补齐多轮审批。
