认证智能体需求总结：

这是一份认证智能体的产品需求文档（PRD）。我已通读全文。先确认一下项目当前状态：工作区里只有这份 PRD 文档和「图片和附件」素材文件夹，没有任何代码实现。所以目前处于需求定义阶段，尚无功能落地。

下面是完整分析。

一、项目要解决的核心问题
这是一款面向家电（主要是电视整机）认证业务的 AI 智能体，目标是把认证全生命周期里高度依赖人工的环节自动化，实现「数据—资料—审批—获证—预警」全链路闭环。

面向用户：研发工程师（结构/电源/电路/光学/声学）、认定工程师、认证工程师、认证管理人员。

预期价值：节省约 8000 人工时，防范认证一致性检验不合格。

二、要实现的功能任务（按认证流程拆解）
我把 PRD 里散落的需求整理成一条主线，共 9 大功能模块：

1. 提出认证需求（自动生成认证申请单）

产品包发布后，产品经理点「创建认证申请单」，AI 自动从产品包和 PLM 抓取字段生成草稿。
规则明确：认证类别取规格书「安全和认证要求」、商标取「品牌」、电压取「电源及输入范围」；持证人/制造商/生产工厂固定；机型、CB 国家差异、报备型号由人手填。
需要建立字段映射 Excel（字段名 + 优化项 + 信息获取位置）。

2. 产品认证计划制定 —— 归到「项目 WBS 计划智能体」（他人负责）。

3. 准备认证资料（这是最重、最核心的模块）

CCC-内销-全新：从 PLM 导出关键件清单文件，AI 按规则审核并输出《安全&EMC 关键件清单》审核结果。
CCC-内销-变更/开发：把「PLM 新导出清单」和「派生原报告清单」两份文件输入 AI，实现智能合并（重复合并、非重复整合并标红加粗、备注来源），生成汇总版关键件清单 + 变更前后对照表；并 AI 推荐最合适的变更原证书型号（对比相同电源板/主板）。
CCC-内销-变更/物料扩点（价值量最大，25000H/项目）：
用物料号在 PLM 反查所有应用机型；
结合状态字段（退市可删，但要参考 SCP 13+9 计划防尾单）筛出在产机型；
逐一排查每个机型的认证报告 PDF 是否已包含拟扩点供方信息，标注「已报备/未报备」；
提取未报备机型清单，按证书号分类；
对 Class B 关键件生成《CCC 认证变更简化流程申请及评估表》。
CB-外销-全新：同 CCC 审核 + 自动生成认证铭牌（从 1TE BOM 的 1063886 物料号抓电压功率）+ 派生差异分析（按位号比对电源板组件，找差异最小的 Top5 组件号）。
4. 审批认证申请：关键件清单（Word）与认定工程师的「零部件认证信息库」（Excel）比对，以（关键件名称+型号+规格）为检索键，识别差异、缺失补充、标色批注。区分 CCC 和外销（interchangeable 规则不同）。

5. 确认报告草稿准确性：比对海信提供的认证资料与认证机构报告草稿，输出差异（两种标识：草稿内批注 + 汇总编号列表）。已有类似系统可参考。

6. 归档、管理、更新证书和报告：证书报告自动同步到云盘 + 档案室 + PLM；有效期管理与预警、到期自动发起延期。

7. 要求及接收供方更新认证信息：AI 审核供方填报信息、证书存续状态；在多个官方网站（CQC、CNCA、VDE、UL、TUV）自动查询证书有效性，临期/暂停时通知。

8. 费用分析 —— 归到「项目费用管理智能体」（他人负责）。

9. 声明材料批量生成 + 认证指标看板：按模板批量生成声明材料转 PDF；从多维表格/PLM/Tims 拉数据生成认证进度、周期、及时性、符合性看板。

三、项目难点
PRD 里已明确标注了几处「技术难点」，加上我的判断：

1. PDF 解析准确率（文档反复点名的最大难点） 认证报告、试验报告大量是 PDF，格式不统一，要从中精确提取「关键件的报备供方信息」。物料扩点场景明确写了「存在技术难点（PDF 文档）」「AI 解析准确率」。而非功能需求却要求准确率 100%——这对 PDF 抽取几乎是不可能达到的硬指标，需要重新协商或引入人工复核兜底。

2. Word/Doc 文档的结构化解析与回写 关键件清单是 .doc 表格，变更场景要求「合并、标红加粗、加批注、备注来源」，还要生成变更前后对照表。一份报告里关键件可能带多个电源板、名称重复需全部提取——表格结构复杂，读写都难。

3. 多系统集成与接口开放 依赖 PLM、TIMS、云盘、SRM、KOA、SCP、集团档案室等多个系统。档案室「需要开放 API 接口」、SCP「13+9 计划接口需确认」，很多接口现状未定，属于外部依赖风险。

4. 派生差异比对的算法逻辑 CB 铭牌/派生差异里要「按位号比对电源板组件物料，找差异最少的 Top5」，这是一个需要清晰规则和 BOM 数据支撑的匹配算法，规则细节还没完全定死。

5. 规则库的动态维护 多处写「如果规则变动，规则库更新」，说明审核规则会变，需要一个可配置的规则引擎，而不是把规则写死在代码里。

6. 官网自动查询的可行性 证书有效性查询要访问 CQC/CNCA/VDE/UL/TUV，其中「需要验证（验证码）」「UL 需账号密码」，自动化爬取有合规和稳定性风险。

7. 100% 准确率 / 100% 可靠性的硬性指标 性能要求写「时间≤50s、准确率 100%」「系统可靠性 100%」。对 AI 类系统这是不现实的验收标准，需要转化为「AI 初审 + 人工确认」的定位。

四、需要注意的事项
1. AI 定位是「辅助」而非「替代」 文档几乎每个环节都保留了「认定工程师确认」「经审核通过后点确认」。产品应定位为人机协同：AI 出初稿/差异点，人做最终决策。这既是业务安全要求，也是应对准确率难点的兜底。

2. 前置条件依赖大

产品规格书必须放到规格下第一级文件或结构化（依赖「项目管理智能体」）；
SRM 与 PLM 对接（白电已用，需确认电视线可用）；
多个「接口确认」「规则确认」的待办还没闭环。 建议开工前先把这些前置项和外部接口锁定，否则会阻塞。
3. 需求边界与协作分工 文档里 WBS 计划、费用分析明确划给了其他智能体（闫伟玲、赵英芹负责），本智能体不做费用核算（第 7、8 步标注「不需要」）。要避免功能越界。

4. 数据/知识依赖需要业务方配置 零部件认证信息库、字段映射 Excel、各类声明模板、interchangeable 规则等都需业务方提供并持续维护，属于「运营配置需求」。

5. 版本与评审状态 当前 V1.0.1，是第一次 PRD 评审后的更新版，第六章功能说明是核心。文档末尾的「功能列表」「评审结果」「数据/调研/设计分析报告」都还是空的，说明 PRD 本身尚未定稿。

6. 建议的落地优先级 按价值/可行性看，我建议：先做关键件清单审核和报告草稿比对（价值高、边界清晰、可用 AI 文档比对能力）→ 再做物料扩点排查（价值最大但依赖 PDF 解析，风险高）→ 最后做归档管理和看板（依赖系统集成）。
