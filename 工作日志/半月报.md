# 半月工作报告

## 一、总体概述

本阶段以**认证智能体项目**为主线，同时推进**项目二熟悉**、**爬取项目预研**，并参与**校企合作与学术交流**。

核心工作立足点：不局限于"认证清单整合"单一功能，而是以该场景为首发，**搭建一套"核心引擎与业务/编排/前端解耦"的可复用文档智能核对框架**，可迁移到规则审核、证书推荐、物料扩点排查等其它文档核对业务。清单整合是这套框架落地的第一个应用。

## 二、项目一：认证智能体 · 变更-开发关键件清单整合

**业务目标**：两份 Word 清单（原始清单/旧版本 + PLM 导出/新版本）→ 判断差异 → AI 归纳 → 人工确认 → 生成【整合清单】+【变更前后对照表】，并沉淀反馈持续优化。

### 2.1 框架搭建（可复用资产）

以 `compare_core` 独立核心包为中心分层解耦：

| 层 | 模块 | 可复用性 |
|---|---|---|
| 解析层 | Word 解析（python-docx 无 COM 线程安全）+ `.doc→.docx` 自动转换 + 视觉解析路线框架 | 任何 Word/表格文档结构化均可复用 |
| 数据模型 | 通用行模型 Row / DiffItem / GroupDiff / AuditReport | 换业务只需调整字段映射 |
| 比对层 | 三级匹配 + 行级数据守恒 + 关键件组抽象 + 数据守恒审计 | 任意"两份清单对比"场景通用 |
| 规则层 | 正向 + 反向规则（YAML 驱动，归一化消除假差异） | 规则外置，换业务改 YAML 即可 |
| 归纳层 | Suggester 抽象（Mock/LLM 可插拔，OpenAI 兼容接口） | 可接任意 LLM，已验证 DeepSeek V4 |
| 编排层 | LangGraph 图 + 顺序 pipeline，共用同一套节点函数 | 节点为单一事实源，图/顺序/Web 三处复用 |
| 记忆层 | 用户决策反馈 JSONL 落盘 + 相似检索 | 人在环反馈闭环通用 |
| 交付层 | 结构化 Word 输出 + 字体/繁简规范化 + 审计补录 | 输出模板可替换 |
| 应用层 | FastAPI 后端（JWT + 异步任务）+ React 前端 | 换业务只改差异展示，骨架通用 |

> **关键设计**：`parse / judge / suggest / human_review / apply / audit / repair / memory` 节点是唯一事实源，被 LangGraph 图、顺序 pipeline、Web 后端三处复用。换业务时只改节点内部逻辑，编排、人在环、Web 全部自动继承。

### 2.2 本阶段具体工作

- **需求与架构**：通读 PRD，抽象全项目 5 类核心能力，选定清单整合为 MVP，产出需求/实现/CCC 分析文档链。
- **核心引擎 + LangGraph 编排**：端到端跑通"解析→判重→建议→人确认→生成→记忆"闭环，核心引擎可脱离 LangGraph 单跑。
- **解析器攻坚**：修复分组标题误入、纵向/横向合并单元格错位、非法控制字符 4 类真实数据坑；根治 Word COM 悬挂，改 python-docx + 子进程转换。
- **三类输出问题修复**：① 行丢失 bug（行级多重集对齐）② 繁体字（opencc 繁→简）③ 输出格式（还原表1/表2结构、分组行、来源标注、标红）。
- **匹配算法迭代**：分组 group 纳入匹配键（修复跨组同型号误配）+ 三级匹配（rich→loose→fuzzy 名称前缀）+ 分趟匹配（修复贪心错配）。
- **组级抽象 + LLM 归纳**：抽象"关键件组"层表达业务动作，接入 DeepSeek V4 归纳变更前后对照表。
- **A/B 角色定稿 + 合并策略闭环**：确认 PLM=新版本=输出骨架、原始清单=旧版本=保留项；旧版本独有项按组归位、不丢行。
- **Web 前后端**：FastAPI 后端 + React 前端（登录/工作台/差异确认页，A/B 字段级对比高亮、一键接受、下载）。
- **数据守恒审计（本阶段重点）**：LangGraph 流程加审计节点 + 补录条件分支，三层校验（引擎层/决策层/物理层），物理层按指纹定位丢行并自动补录自愈。
- **版本管理与文档**：三次版本快照归档 + 全程工作日志。

### 2.6 思考

项目一最大的收获，是认识到"难点不在算法而在业务语义对齐"。最初用物理行做 diff，看似合理却表达不出"电源单元换型"这类业务动作，直到抽象出"关键件组"才对上业务视角——数据的组织粒度比比对逻辑本身更关键。其次，把"数据守恒审计"作为可信度保障，让系统不仅能合并，还能自证不丢行，这对认证这种强合规场景尤为重要。最后，坚持核心引擎与编排、前端解耦，使清单整合沉淀为可迁移的通用框架而非一次性脚本。不足是仍依赖单一样例，跨机型稳定性与部分业务规则边界待验证。

### 四、五 思考

爬取项目与校企合作/学术交流本质上是同一件事的两面——都在"引入外部成熟成果为我所用"。爬取项目通过复用 baseline 快速起步，学术交流则从会议与前沿资料中获取图像增强、AVS 等有参考价值的模型；比起从零自研，这种"站在已有成果上再改造"的方式更稳、更高效。关键都在于落地——外部成果不能照搬，要结合海信实际业务场景做适配与筛选，明确数据源、稳定性、合规边界以及与业务的结合点。下一步是把调研成果系统整理，评估其与海信场景的契合度，转化为可落地的改造方案。
