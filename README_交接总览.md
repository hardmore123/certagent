## 1. 这个项目做什么

两份 Word 关键件**清单**（A=原始/旧版本、B=PLM 新品/新版本）→ 判断差异 → AI 建议 → 人工确认（接受 / 拒绝 / 手动匹配纠正 / 其实相同 / 拆两独有）→ 生成【整合版关键件清单】+【变更前后对照表】，并把决策沉淀进长期记忆用于持续优化。

关键动词是**合并 / 整合**（不是"核对"——核对是项目二做的事）。

状态：**已完成、已部署上线、已上传 GitLab**。

## 4. 架构（分层，依赖单向）

```
CLI(cli.py) / Web(webapi) → 编排层 graph/(LangGraph,可选) → 核心引擎 compare_core/(独立可单跑)
                                                            解析 → 判断(diff) → 建议(规则+LLM) → 写Word → 记忆
```

- **核心引擎 `compare_core/`** 不依赖 LangGraph，可 CLI 直接跑（默认）。
- **`graph/`** 用 LangGraph + `interrupt` 实现人在环（`--engine graph`）。
- **`webapi/`** FastAPI Web 服务，前端确认页人工决策。
- **`frontend/`** Vite + React，确认页 ReviewPage。

核心引擎子模块（两版本均有）：
| 子模块 | 职责 |
|---|---|
| `parser/` | .doc→.docx 转换（Word COM / LibreOffice）+ 表格解析（容错重心：合并单元格、列错位、非法字符清洗） |
| `differ/` | 归一化 + 匹配键对齐 + 差异分类 + 置信度 + 决策解析(resolve) + 审计 |
| `rules/` | 正向规则 + 反向规则（误报防护，YAML） |
| `suggester/` | 建议：规则化动作 + LLM/mock 变更项归纳 |
| `writer/` | 生成整合清单 + 对照表 docx（批注/高亮） |
| `memory/` | 决策落盘 + 指纹聚合读回 + 反哺建议（详见 `记忆库说明.md`） |

里程碑：M1 解析 · M2 diff · M3 编排出整合清单 · M4 人确认 · M5 LLM 对照表 · M6 记忆闭环

## 5. 输入 / 输出

### 输入（两份 Word 清单）
- A = 原始/旧版本清单（原报告清单，人工已整理）
- B = PLM 新品/新版本清单（PLM 导出清单）
- 支持 `.doc` / `.docx` / `.json` 三种输入；`.doc` 自动转 `.docx`（Windows 用 Word COM，Linux 用 LibreOffice）
  > ⚠️ **服务器版只接受 `.docx`/`.json`，拒绝 `.doc` 上传**（LibreOffice 在 systemd 下不可靠）。详见 `工作日志与周报/部署与使用指南.md`。

**输入格式要求（表头/表格结构/字段要求，不满足会解析失败）详见 `数据结构与实现思路详解.md` 的「第一部分补充：输入格式要求」**——这是接手必读，包含：
- 表头别名表（`HEADER_MAP`，哪些表头写法能识别）
- 表1/表2 编号规则与证书号取值逻辑
- 合并单元格/分组标题行/跨行填充的容错处理
- 匹配键（`关键件名称`+`型号`）与比对字段
- 不满足要求的后果对照表

详见 `输入样例/`。

### 输出
- **整合版关键件清单.docx**（合并后的完整清单）
- **变更前后对照表.docx**（逐项差异对照，含批注/高亮）
- 运行产物 JSON（diff/changes/group_diffs/suggestions/audit，便于追溯）

详见 `输出示例/`。

## 7.5 当前进展与待开发（接手必读）

### 已交付能力

项目一已跑通"两份清单 → 差异 → 建议 → 人工确认 → 整合清单 + 对照表"的完整闭环，具体包括：
- **文档解析**：`.doc`/`.docx` 表格结构化提取（含合并单元格、分组标题、跨行填充容错），`.doc` 自动转 `.docx`。
- **差异判断**：归一化 + 匹配键对齐（关键件名称+型号）+ 四态分类（SAME/CHANGED/ONLY_ORIG/ONLY_PLM）+ 置信度 + 型号集合匹配（一格多型号）。
- **AI 建议**：规则化动作 + LLM/mock 变更项归纳，生成对照表。
- **人工确认**：五态决策（接受/拒绝/手工修改/拆分/合并）+ 长期记忆反哺。
- **输出**：整合版关键件清单.docx（标红加粗+来源备注）+ 变更前后对照表.docx（词级高亮）。
- **Web 服务**：多任务异步 + 使用统计 + 服务器部署（含透明加密文件解密）。

### 当前对比范围（仅两份文档全量比对）

**项目一目前仅支持两份文档进行对比**：一次任务接收 A（原报告清单）+ B（PLM 导出清单）两份输入，按固定的 6 个比对字段（位号、规格材料、制造商、生产企业、认证标准、证书号）对**全部匹配上的行**做全量逐字段比对。

### 待开发：对比内容筛选

**关于对比内容进行筛选这部分还待开发**。具体指以下能力目前**尚未实现**：
- **字段级筛选**：让用户选择"本次只比哪些字段"（如只比规格材料和制造商、忽略认证标准），当前固定全比 6 个字段。
- **范围/分组筛选**：让用户选择"只比某些分组/某些关键件"，当前对全部行全量比对。
- **比对策略可选**：如严格模式/宽松模式切换、是否启用型号集合匹配的开关面板化等。

> 现有的"筛选"仅指前端对**已生成的差异结果**做查看筛选（如只看待确认项、只看 CHANGED），以及 LLM 智能配对的勾选开关——这些是结果展示层的筛选，**不是对比内容的筛选**。对比内容（比什么、比哪些字段、比哪些行）目前在规则文件 `merge_rules.yaml` 里硬编码，未提供用户可配置的筛选入口。

> 拓展设计里的"变更类型/责任专业/处理动作/优先级 → 做筛选看板"（见 `拓展设计与原型/`）属于规划稿，尚未实现。

## 9. 与项目二的边界与关系

本项目（项目一）做**清单整合**；工作区另有一个项目二"报告草稿准确性核对（ReportVerify）"，做**核对**。两者边界见 `需求与设计文档/两个项目导读.md`。本交接包**只含项目一**，项目二相关目录（`报告草稿准确性核对/` `确认报告草稿/` `确认报告草稿样本/` `report-verify-demo/`）未纳入。

### 项目二与项目一的关系

**项目二（报告草稿核对）是基于项目一的逻辑，在"报告草稿核对"这一新场景下的应用**。具体而言：
- **复用的内核**：项目二沿用了项目一"Word 表格结构化解析 → 匹配键对齐 → 逐字段差异 → 人工确认"的确定性核对内核，底层表格遍历思路一脉相承（项目二 `document_parser.py` 底层沿用 list-merge-demo 的 grid/table 思路）。
- **新场景的改造**：项目一把"两份清单整合成一份"（合并去重 + 标注新增/差异），项目二把"CERT 超集 vs DRAFT 草稿"核对出"哪里对不上"（不合并、只批注 + 编号汇总）。因此项目二增加了表头指纹子块定位、DRAFT 批注锚点、CERT/DRAFT 方向不可交换、双输出一致性校验等新机制。
- **代码独立**：项目二是独立代码库（`报告草稿准确性核对/`），不依赖项目一运行时，但设计思想上继承项目一的"先结构化、后智能化、确定性优先、人在环确认"。

> 一句话：项目一是"把两份清单合成一份"的整合工具，项目二是"拿 CERT 基准核对 DRAFT 草稿"的核对工具——同一个核对内核，两个不同业务场景的应用。
